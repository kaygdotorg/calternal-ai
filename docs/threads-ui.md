# Threads screen on the real server

`apps/web/src/server/threads-client.ts` is `ThreadsClient` (the one interface the Threads app talks to) over the orchestrator's operations (`threads.list/get/create/send/stop/archive/delete`,
[threads.md](threads.md)) and the job event stream ([agent-turns.md](agent-turns.md)). `?server=1` selects it (development token mode, as Notes); the fixtures stay the default, for the preview and the tests.
Response shapes and the Markdown are in `server/thread-file.ts`; `server/threads-client.test.ts` runs the adapter against a recorded-response double of the server (shapes from `crates/server/src/threads`).

| Screen | Server |
| --- | --- |
| Sidebar list | `threads.list` (the shell's current space): turn state, provider, model, mode, message count, last activity, parent. One operation, no file read. Kept current by the space's live journal (`server/space-feed.ts`), never polled |
| Turn state | applied in place from `threads.turn_state_changed` journal entries (`data.state`, `data.job_id`) |
| Open a thread | `threads.get`: the Markdown is parsed once per revision (message times from the markers); messages are read in ranges from the parse. A saved message or checkpoint of the open thread re-reads it (coalesced 120 ms) |
| Reload mid-turn | `threads.get` names the running job; the page follows its job stream from the last event it saw |
| Send | `threads.send` with the caller's request id; the composer's permission mode, provider and model travel with it (the server applies them directly) |
| Working state and steps | the job's SSE stream: provider events are nested, `chunk.data.event` (`text_delta`, `tool_started`, `tool_finished`); at its end the file is re-read for the saved answer |
| Stop, rename, archive, unarchive, delete | `threads.stop`, `.rename`, `.archive`, `.unarchive`, `.delete` |
| Request bar (questions, approvals, secrets) | `ServerRequests` (`server/requests.ts`) on the requests lane's operations (`docs/requests.md`): `requests.list` (account-wide, `{}`), `requests.answer` `{id, answer}`, `requests.approve` `{id, lifetime: once or this_thread}`, `requests.deny`; a secret's value goes to `POST /api/v1/auth/secrets/provide`. The bar offers "Allow for this thread" only when the server's `detail.lifetimes` lists it (`lifetimesOf` reads that list and infers nothing; none listed means once only). Approving needs a fresh passkey proof on an installation session: a development bearer is refused and the server's words are shown. Refreshed when the feed says a turn started or stopped waiting |

Tested against a recorded-response double (`threads-client.test.ts`) and, end to end, against a seeded installation (`e2e/live-threads.mjs`).

## What the server still lacks

- Where a thread runs: no operation names or records a machine; the choice is kept on the page and the server picks one.
- Changes and Run tabs have no operation.

## The client interface

`ThreadsClient` (`apps/threads/client.ts`) is the threads themselves (list, get, create, delete, messages, watch, send, stop, rename, archive, unarchive) plus three smaller interfaces a server
serves from separate operations: `ChoicesClient` (provider and model, permission, machines, where it runs; on the server these travel with `send`), `RequestsClient` (list, watch, answer) and
`PanelsClient` (Changes and Run). The split is type-level, with no change in behaviour; the server adapter delegates requests to its own small class and the fixtures implement all four in one.
A further step, not taken because it would only add code today: components taking the narrow interface they use (the request bar takes `RequestsClient`, the composer `ChoicesClient`), so a screen can run
on a server that serves only part of it.

## Checkpoint additions, tool steps and `thread_full` (2026-11-18)

- **Delta read.** The journal's `threads.checkpoint` entry carries the revision it reached and the byte range it added. `ServerThreads.advance` applies entries in order: when the held revision is the entry's base it calls `threads.get` with `since` (the entry's `data`), splices the returned bytes into the body at `offset` (`server/thread-delta.ts`: the body is held as UTF-8 bytes, because offsets count bytes) and parses again only from the message marker at or before the insertion. A different base revision, a `conflict` (`checkpoint_unavailable`) or an offset that cannot be placed falls back to one whole read. The end of a job stream no longer reads the thread: its saved checkpoints arrive as additions. Opening a thread reads it once (the header's read a moment earlier is reused). Whole reads remain for `threads.send` entries, a journal reset and an explicit reload.
- **Tool steps.** Live: `tool_started` carries `name` and `summary` (the bounded target, "Run ls"); the step's title is the summary and its detail the tool name. Saved: one blockquote line per event, `> Tool <name> · <what> (started | N bytes of tool output | finished | failed)`; `blocksOf` folds them into a `steps` group (words between steps split the group), so a reload shows the same steps. Output text is not stored in the file (a byte count only), so a step's output reads "N bytes of output".
- **`thread_full`** (a checkpoint past 2 MiB fails the turn): `reasonNotice` maps it to the `thread-full` notice, "This thread is full", with a New thread action (fixture scenario `?scenario=full`). Sends are left to the server to refuse.
- **Checks.** `e2e/steps-server.mjs` runs the repo's fixture provider (`scripted-tool-steps`, success, failing step, 96 KiB output, stop mid-step) on a real server and compares what the page built from additions with a whole read. `e2e/server-double.mjs` now keeps revisions and answers `since` like the server.

## Composer expand and collapse (2026-11-18)

The owner asked for the focus/blur motion ChatGPT and Claude have. Sources read: the bb plugin thread `thr_mfnshymcbk` (its log and `~/Developer/bb-plugins/calternal-ui`: `AGENTS.md` "Phone composer focus morph", `frame/composer.ts`, `frame/pills-composer.ts`, `frame/keyboard-follow.ts`) and the owner's iPhone recordings in its Attachments (`ScreenRecording_11-15-2026-22-55-44_1.mp4` and `..._23-09-25_1.mp4` are ChatGPT's and Claude's apps; the others are the plugin on a phone). The plugin's settled values come from its measurements of the owner's 60 fps recordings:

| What | Settled value | Here |
| --- | --- | --- |
| Unfocused | one-line capsule, 52 pt; 38 pt from the screen edges | the context row and the chips row leave the layout; on a phone or narrow window the box takes 26 px more inset a side |
| Focused | two rows, 12 pt from the edges | all three rows; full column width |
| Radius | one value in both states | the pane radius in both: corners never jump |
| Duration and curve | 350 ms on the iPhone keyboard's own measured track (a `linear()` fit, 21 samples) | tokens `--dur-morph` 350 ms and `--ease-morph`; 1 ms under reduced motion |
| Order | width, height and the button row are one motion; it starts at the tap (focus), the close at the blur | one flip of state; the motion plays from the old look on the same clock |
| Interruptible | yes | a flip that begins mid-morph starts from what is on screen (`e2e/composer-fold.mjs`: largest step 9 to 17 px over a reversal at 120 ms) |
| Keyboard | keyboard actions never animate | Tab into or out of the composer changes state at once (and under reduced motion or "motion off") |

**How it is drawn (`apps/threads/fold.ts`, no layout per frame).** The state flips at once: the composer is laid out in its new form in one layout. Before the DOM changes the old look is read, after it the motion is played from it (the technique called FLIP): the glass layer's top, right, bottom and left offsets (a leaf with no children), the field and the button as `transform`, the rows that appear as `opacity` and a small rise, and the rows that go as faded copies. The first version animated the grid rows and a margin, which laid out and recalculated style every frame; over the 700 ms window at 4x CPU the trace went from UpdateLayoutTree 74 to 17 ms and Layout 38 to 10 ms on a phone (63 to 16 and 13 to 6 on a desktop), and the first key after a click from 8.5 to 8.0 ms (7.2 with no fold at all; later keys 3.6 ms either way: `e2e/profile-fold.mjs`, `e2e/ab-key-work.mjs`).

State: open when the composer or one of its menus has focus, or a mention picker is open, or a press that began inside an open composer is still down (a button that takes the focus on press, or in Safari does not take it, must not lose its row before the click); closed otherwise, even with a draft. A mouse press on Stop or Send of a collapsed composer does not unfold it (it would move the button from under the pointer). Focus is read after the event; a window losing focus keeps it open.

**The message list moves with the composer, as in ChatGPT's and Claude's apps.** The owner's recordings show no gap above their collapsed composers: the last message sits right above it, and when the composer grows (with the keyboard on a phone) the conversation moves up with it. The first version reserved the expanded height and left a 70 px gap above a collapsed composer; that was dropped. `ThreadView` keeps the list's bottom inset equal to the measured height of what floats under it; a list that was at the bottom stays at the bottom when that height changes (a multi-line draft, a bar appearing, the composer folding), and at a fold the content also slides by the difference as a transform of the list's content over the same time and curve (`cmp-fold` event), the request bar and notices above the composer as well, so a press that began on them still lands. A list scrolled away from the bottom does not move.

Cost while typing: none (the state does not change per key). Checks: `e2e/composer-fold.mjs` (desktop and phone: the layout is in its new form from the first changed frame, the glass runs about 350 ms, the last message stays just above the composer in both states and moves with it, reversal without a jump, keyboard and reduced motion instant) and in the e2e gate.

Approvals for irreversible or access-widening actions are single-use (owner, 2026-11-18): the server lists `once` only for them, and the bar offers nothing else (`lifetimesOf`).

## A turn from the send, who wrote a message, the spinner, the picker (2026-11-18, owner feedback)

- **Working from the moment of the send.** `Conversation.begin()` shows the Working row at once ("Sending") and takes it back if the send is refused. The row pulses (`.pulse`, bb's) and says what is happening: Sending, Waiting to start, Starting the machine (the job is running, no provider event yet), Thinking (the provider's `session`/`start`, and after each tool), the tool's own summary while it runs ("Run ls"), Writing. The adapter derives these from the job stream (`snapshot`/`state`, the `placement` chunk, the provider events); the fixtures script the same. Above the row, folded: the reasoning (`Thought.svelte`, "Thinking" and pulsing while it goes) and the steps so far (`Steps`, "N tools"). When the turn ends the message replaces the row with the same blocks collapsed: "Thought for 4 s" and "Worked for 12 s · 3 tools". The person's own message arriving does not end the row (only the turn's agent message does). A message the file records no duration for gets the one this page measured (`carry`); what the file records wins.
- **Who wrote a message.** An assistant message has `by` (provider, model, reasoning level, duration); its provider's icon is at its left (`ProviderMark`), the rest in its tooltip and accessible name ("Claude Code, Sonnet 5.5, high reasoning, took 12 s"). **Source today: this page only.** The thread file's opening and `turn-timing` markers are the backend lane's proposed readable format (`docs/threads.md` on `origin/lane/turn-meta`, "Proposed readable file format"), which waits for the owner; nothing here parses them. So a turn this page saw carries the provider, model and level the thread had when the person sent and the time it measured (`Conversation.carry`); a message read from the file shows the thread's current provider and nothing else, until the format is decided and read.
- **Models, phases, reasoning (against the turn-meta lane, `docs/reviews/turn-meta-2026-11-18.md`).** The picker's providers come from `threads.models {space_id}` (`providers[].models[].reasoning_levels`, `default_model`); a server without it keeps the one default model and says so. A send carries `model` and `reasoning` (validated by the server before the message is saved). The Working row's phases are the job stream's `turn_phase` chunks (`queued`, `starting_sandbox`, `running`, `thinking`, `running_tool` refined by the tool's summary, `waiting_on_person`), from the moment of the send; reasoning is `reasoning_started`, `reasoning_delta {text}` and `reasoning_finished {duration_ms}` frames, shown in the folded block ("Thinking", then "Thought for 4 s"). The file keeps the reasoning's timing only, so the block's text lives for the session.
- **The spinner stepped** because `Spinner` ran `spin 0.9s var(--ease-out) infinite`: an easing curve applies to each turn, so it sped up and slowed once a turn; and in keyboard use `base.css` zeroed every animation duration, which stopped it (and the resume steps). It is now `linear`, and spinners, pulses, shimmers and the caret are exempt from the keyboard-use zeroing. `rotate` runs on the compositor (checked in `e2e/turn-ui.mjs`: linear easing, a non-zero duration after Tab).
- **The model picker.** The server has no list of a provider's models yet, so in server mode a provider offers only its default (`ProviderOption.listed: false`). The picker says so on the row ("models are not listed yet") and a search that finds nothing answers "This provider's models are not listed yet. It uses its default model." (`Menu` has a new `empty` text). When the backend operation lands, `listed` is true and the models come from it.
- **One material.** Every menu, popover, picker and sheet in this area is the shared `Popover`/`Sheet` over `Panel` (the one glass); `Tooltip` and toasts are the shared ones. What the owner sees as an opaque white sheet is that shared surface: `Popover` and `Sheet` default to `dense` (+0.16 of tint alpha, against the composer's plain glass), which on a bright wallpaper reads as solid. Changing the density or the readability floor is a change to the shell's material, not to a surface here (raised with the lead).
- **The thread's overflow button** (card header, top right, in a pill) opens the sidebar row's menu: `thread-menu.ts` is its one definition (rename, move to a section, copy link, stop, archive); Rename starts the title edit in the header.

## A rail of marks for a long thread (a question, not built)

bb has a strip at the left edge of a long thread that appears on hover with one mark per message, each a jump target. Built here it would sit beside the virtual list, with three parts.

1. **Data.** The rail needs only an outline: the count and, per message, its role (and time, and for a person's message its first line for the hover preview). `ServerThreads` already parses the whole file, so it can hand out `outline(): {role, at, preview?}[]` for nothing; the fixture client likewise. A 10,000-message thread is 10,000 small records, not 10,000 elements.
2. **Drawing.** Marks are not DOM nodes: one `<canvas>` (or an SVG sprite) the height of the card, one tick per message at `index / count` of its height (a person's message longer and in the accent, an agent's shorter), redrawn only when the count changes or the pointer moves. The rail is a 12 px hit strip at the card's left edge that widens to about 40 px on hover or focus (`prefers-reduced-motion`: no widening animation); the mark under the pointer grows and shows a tooltip with the preview. Keyboard: the strip is one `role="slider"`-like control (Up and Down move between person messages, Enter jumps), so it costs one tab stop.
3. **Jumping.** `VirtualList` needs one new method, `scrollToIndex(i)`: `scrollTop = prefix(i) + topInset` from the Fenwick tree, then the measure pass corrects what the estimate got wrong (the list already keeps what the reader sees still while rows above it measure). The row is highlighted for a moment (an accent veil fading over `--dur-slow`, no motion under reduced motion). A message not yet read is fetched by the conversation's page read first (`ensure`), so the jump never lands on a placeholder.

As its own plugin (`calternal-orchestrator-rail`) it needs: a contribution point in the Threads app for a thread-side view (a slot next to the list, with the list's size), a read it can bind to (`thread.outline`: the outline above, bounded and paged for very long threads) and a host call to act (`thread.scrollTo {index}`, `thread.highlight {index}`). Plugins here are TypeScript and portable GenUI first, so the honest way is a GenUI component (`Rail`: marks `{at, kind, label}`, an `onpick` action, a hover preview) that the browser draws with the canvas above and the native client draws with its own view; then the plugin is a small program binding `thread.outline` to `Rail` and `onpick` to `thread.scrollTo`, and no plugin code runs on the hot path. What is not portable GenUI today is the hover widening and the canvas; those live in the shell's `Rail` renderer, not in the plugin. The owner's decision to take: whether the rail is the orchestrator's (shipped with it, off by default) or a separate optional plugin; and whether it appears from a thread's first message or only past some length (bb shows it from the start).

## Editing a sent message (a question, not built)

**What it means elsewhere.** ChatGPT and Claude (web and apps): editing one of your messages and sending it **creates a branch**: the thread shows the edited message with a small "1 / 2" switch; the replies after the original message are not deleted, they stay on the other branch; the new branch continues from the edit, so everything after the edited message in the visible branch is replaced by the new answer. bb does not rewrite in place: it **forks**: its `thread fork` starts a new thread from a chosen point of the old one (its CLI takes a source event sequence), leaving the original untouched; the new thread's agent starts from that history.

**What ours allows today.** A thread is one Markdown file of messages with markers, only ever appended to (checkpoints add bytes; the page applies them as additions). Removing or changing a message in the middle is a different kind of change (the journal then says "read the whole thread"), and nothing in the file says which messages belong to which branch. A send continues the provider's own session (`--resume`), whose context holds every turn after the edited message too; the session cannot be rewound, so after an edit it must be started fresh with the earlier messages handed over as a transcript ("cross-turn transcript handoff remains turn engine integration work", `docs/threads.md`) or forked (Claude Code can fork a session when resuming, other providers may not).

**Options and costs.**
1. **Edit as a fork (recommended first step).** "Edit and resend" on a message makes a child thread (`parent_thread` exists, the sidebar and the thread view already show children) containing the messages before it plus the edited one, and sends it. The original is untouched, nothing is deleted, no branch grammar is needed. Cost: the transcript handoff (or a session fork) for the new thread, and the person finds the edit in another thread rather than as "2 / 2" in place.
2. **Truncate and resend in place.** Delete everything after the message, replace it and send. Cheapest to explain, but destructive (the answers are gone unless the Trash keeps the file's earlier revision, which it can: content revisions are retained), it breaks the append-only reads (a whole read after every such edit) and it needs the same transcript handoff because the provider session still holds the later turns.
3. **Branches inside the file** (ChatGPT's model). A branch marker on messages and a "1 / 2" switch. The nicest result and the biggest change: the marker grammar, the delta read (offsets within a branch), search, the message count, resume (one provider session per branch) and every client all change. Worth deciding only if the owner wants the in-place feel.
4. **Edit only the last message while it has not been answered** (or is queued). No history is touched; it is a small change to the pending send. Useful alongside any of the above, not a substitute.

**Recommendation.** Start with option 1, and add 4 where it is free; defer 3 until the file format is settled (the owner's pending decision on the readable format is the natural moment). The question to take to the owner: is a fork enough ("edit makes a new thread"), or must the thread itself branch?
