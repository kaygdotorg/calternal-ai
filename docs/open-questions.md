## Recently decided (2026-11-17), now in the decision records

- Order of work (kayg, 2026-11-19 evening): the spaces and plugins API is made stable, solid and tested first, in whichever order takes the least time; only then is everything refactored into real plugins (Notes on the web is not at parity yet either), so the question of a native note editor waits until then. A plan buys compute and apps. Web keyboard navigation merges now with the slow-device churn stall kept as an open defect, optimising continues until that gate is met.
- Sharing one item across spaces (kayg, 2026-11-19 evening): a shared note, task or thread never leaves its home space and its plugin always runs there, with a ticket that names the guest and limits them to that item; "Shared with me" is a host feature; the guest needs no plugin installed because the interface is a description. A guest's activity uses the owner's quota. A thread can be shared to view, to comment, or to prompt the agent: Prompt is offered as an explicit higher grant, off by default, with a plain warning, and approvals still go to the owner; "Continue in my space" copies the item so the guest works on their own machine and hours. A public link to a plugin's item serves the last saved view rather than waking the runtime.
- Plugin runtime (kayg, 2026-11-19 evening; replaces the two-tier idea and "one container worker per plugin and space"): every space has its own isolated, long-lived runtime in which all of its plugins run with full power over that space and nothing outside it; official and community plugins have the same API and limits. Decided: (1) on the hosted service the wall is a microVM per space, asleep as a snapshot when idle (subject to the wake and memory measurements); (2) a self-hosted operator chooses the wall, the weaker option plainly labelled; (3) inside a space each plugin is its own process with its own permissions; (4) in a shared space a plugin sees the whole space, the broker still enforces the acting member's rights on every call, and every member can see the installed plugins with their permissions and destinations; (5) no direct network: declared destinations through the server's proxy, approved by the Owner and re-approved when they change; (6) data only through brokered calls to start; (7) gallery plugins in one tap, any other source with a plain warning, pinned by checksum; (8) an agent may write a full plugin, enabled after the Owner confirms. Reading never waits for a runtime to wake (engines and the device cache serve lists and items) and secrets never enter the runtime. Being examined: agents' sandboxes as rootless containers inside the same space microVM instead of a microVM per person.
- Apple apps are native all the way (kayg, 2026-11-19 evening, after comparing builds): the web-app-in-a-web-view shell is dropped as the plan for Apple platforms. The web app's look is the design target (structure, flat sidebar on the base, floating card, glass pills, spacing, single-line rows), built from system primitives that are styled towards it through the system's own customisation points, never replaced by hand-built controls and never stripped of what makes them native (selection, focus and keyboard navigation, Dynamic Type, accessibility, haptics, menus, swipe actions, scroll physics).
- Native apps (kayg, 2026-11-19): the Mac window has one base layer under everything, chosen in Settings, Appearance: Wallpaper (the person's own background, the same as on the web and phone, shown whenever one is set), Frost (the system's frosted window material; opt-in) or Liquid Glass; sidebars and the card sit on that layer rather than being differently coloured panes. Appearance settings are the person's and apply on every device where they make sense. Up and Down move through any list of rows at the fastest key-repeat rate on the web and the Mac, and rendering keeps up: selection paints at once and the main pane loads only when the selection settles. The app capsule stays at the bottom of the left sidebar on phone and desktop, in the native apps too. The title pill is centred at the top on every platform. Native apps use system primitives to the maximum and custom components only with a written reason; Frost on the Mac is an amount (a dial, as in kayg's hermternal-apple), not a switch.
- Interface direction (kayg, 2026-11-19, after trying native chrome on an iPhone: "there is no competing with native apps"): described interface is the main route and each platform draws it natively. A plugin describes its interface (the component catalogue for content, the chrome description for an app's sidebar, header and actions) and the catalogue and chrome description are the centre of the plugin API. Real web code ships only for what description cannot express: today the note editor and sandboxed HTML an agent writes. The Apple apps are native chrome and lists in SwiftUI with a web view as the content card where needed, going native inward over time; the Mac app is tried the same way. The web app draws the same descriptions in Svelte and stays the app for browsers, Linux, Windows and Android. The chrome description must be rich enough for a plugin to reshape the shell (the web lane's 13 gaps are the start). Renderers (catalogue components, host components such as Transcript and Composer, the shell) are ours and exist once per platform; no plugin is written twice and a plugin author never pays that price. This replaces the 2026-11-18 "stateful generated views" wording where they differ and supersedes "portable GenUI first" in AGENTS.md.
