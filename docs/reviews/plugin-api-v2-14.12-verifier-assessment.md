# Revision 14.12 · Verifier assessment for the owner

**Decision.** Should the Python verifier be sealed as part of the
contract, or shipped as a versioned conformance tool while text,
catalogue and wire schemas remain normative? I recommend the second.
Pin the tool and fixture corpus to the revision for reproducibility.
Make verified disagreement a release blocker for the affected surface.
Reserve execution authority and durability claims for real host
qualification.

## What held up in review

Since round 3 the bounded input reader, duplicate-key and path/digest
checks, pinned schema registry, and ordinary declared-field and primitive
wire checks have produced no recurring findings. The library-style
checks are local and have a finite matrix. The 14.10 absolute-end sweep
was an exception in schema value validation and has Python and
ECMAScript coverage.

The round-3 fixes for search scope, operand budgets, empty extractor
outputs and both member audiences closed after testing their adjacent
cases. The subsequent title source issue settled when revision 14.7
required a canonical declaration. The earlier attempt to infer exact
types from arbitrary Draft 7 combinations generated false refusals.
That is a useful precedent for choosing a declaration over an interpreter.

## What keeps producing findings

Activation captures combine authority from multiple replies and a
verified description and manifest. Every extra source of a context
multiplies the cases. The same action can arrive from the initial view,
an ordinary row window, a retained result or a replacement after
renewal. Matching an ID alone misses lease, grant, Bind, row and
purpose. Checking only an issuance path rejects usable contexts from
another path. The repeated findings moved from renewal and aliasing
to Resume confirmation and then to the initial row window and authored
manifest lookup.

Confirmation checks combine host-synthesized material, applicable
manifest inputs, offered request-card actions and their retained
identity. The wire shape alone cannot infer which fields apply.
Presence checks admitted an unrelated entry, while partial allowlists
missed shadowing and display substitution. The checker needs a trusted
expected effect and checked inputs before it can compare a card.
Synthetic fence traces test the expected sequence and cannot establish
that a server actually fenced before a crash. The authority finding in
the failed reattachment path required a contract fix as well as a trace.

## What I would change

1. Generate a capture transition table from the catalogue. Represent
   view, window, renewal, resolve and confirm as distinct steps. Index
   each context by lease, grant, audience, component or Bind, row and
   action. Enumerate issuance, retirement, replay and alias cases from
   those dimensions. Keep the Python walker and bounds as mechanics.
2. Generate challenge material rules keyed by the resolved host action
   or manifest operation. Feed every surface the same checked
   effect/inputs and offered choices. Generate a valid case and a
   missing, duplicate, unchecked and changed-field case for each row.
   Use actual host captures for cross-implementation conformance.
3. Keep parser and schema tests as a fast gate. Compare both renderers
   and the host against the same cases. Gate runtime crash, renewal and
   egress on the real engine, with authority and outcome evidence across
   the actual commit boundary.

The trade-off is explicit. Sealing the current program gives authors one
deterministic gate but would freeze incidental fixture assumptions and
make every discovered capture gap a contract amendment. Versioning it
separately keeps a reproducible gate while allowing corrections to its
model. It requires an owner for disagreement triage and a record of
which semantic checks and host proofs are required to enable each route.
