## Part A — plugins

### A1. What the existing app actually calls a plugin

There is no single extensibility contract covering an entire app. The implementation has several independently wired mechanisms:

| Mechanism | Verified implementation | Consequence for reuse |
| --- | --- | --- |
| App/action plugin | `old:crates/core/src/plugin.rs:1–20,54–118`: `Plugin: Send + Sync + 'static` exposes only `id()` and `actions()`. IDs are lowercase letters/digits/dashes, start with a letter, at most 40 bytes; action suffixes use the same grammar. Registry rejects duplicate plugins/actions and actions outside `<plugin>.<verb>`. | Reuse namespace validation and discovery intent; this is compiled Rust registration, not dynamic TypeScript loading, lifecycle, UI or format registration. ### A3. Format plugins: accepted design versus concrete code

ADR 0048 (`old:docs/adr/0048-format-plugins-run-on-server-and-clients.md:5–23`) calls for Rust crates shared between server and native clients, parse/index/record merge, heavy server-only jobs and preserving unknown bytes. The inspected `core::Plugin` has no format claim/parse/merge interface and there is no general format registry in the inspected core/registration code. There are concrete reusable format implementations:

- **Contacts:** `old:crates/contacts/src/lib.rs:1–23` is an I/O-free codec; contact notes are canonical and original vCard bytes live in a companion file. `old:crates/contacts/src/merge.rs:185–225` merges the actual per-client sent snapshot with returned bytes, preserving unknown parameters; this is domain-specific reconciliation, not a generic three-way JSON merge.
- **Markdown extraction:** `old:crates/markdown-view/src/lib.rs:1–27,43–65,74–85` returns original byte ranges, supports bounded parsing and distinct in-process/worker paths, with an explicit parser/config identity. It is read-only extraction, not a general Markdown serializer/merge engine. Notes editor parser options intentionally can differ.
- **Notes formats and links:** `old:crates/notes/src/props.rs:263` implements frontmatter merge; `old:crates/notes/src/links.rs:1–34` reads/writes relative Markdown note links with anchors and skips code. `old:crates/notes/src/blocks.rs:1–7,67–84` handles block ranges using UTF-16 edit helpers. These are distributed domain modules, not one portable format ABI. Structured frontmatter guards and exact-byte writers require a separate portability audit before claiming shared-code reuse.
- **Tasks:** the Notes describer, frontmatter edits and bounded Markdown extractor form a cross-app extension, not a separate canonical task database. Replacing this with asynchronous TypeScript indexing would lose same-transaction freshness unless a host-mediated projection contract replaces it.
- **Settings:** versioned JSON preservation in Prefs storage is useful, but complete declared-setting validation and accepted conflict behavior must be distinguished from current generic prefs actions and browser policy.

For the rewrite, a format claim needs a format/version identity and bounded recognition rule; choosing the handler is explicit, not “last plugin installed wins.” Parse/index/merge are pure transformations over authorized snapshots. A merge proposal returns bytes plus conflicts/provenance; only the host validates bases, checks authority and commits/history/journals. Compiled default engines can be fast without making product behavior unreplaceable. TypeScript replacements run server-side; native fallback is already settled as opaque preservation. This resolves the old shared-Rust aspiration without inventing a native JavaScript runtime or Wasm.

### A5. Primary worked example: orchestrator first

This trace derives required extension points from accepted behavior; operation names below are illustrative. Evidence: `new:docs/architecture-proposal.md:118–137,317–389,430–458`; `new:docs/feature-gap-assessment.md:19–35,57–69`. It does not implement the UX.

1. **Enable and discover:** enable the orchestrator in a space, provision thread/workflow Collections, register kinds/default handlers/search/settings and the three shell regions. Account-wide search/Activity uses personal scope and independently checked space contributions. A space-installed worker never gets cross-space ambient reach.
2. **Admit a message:** a stable operation identity admits input durably with acting account, space, conversation, provider/account handle, machine/workspace, current grants, code/config version and intended effects. The visible thread/durable message record is protected; product composition and workflows are replaceable. Return admitted/run IDs rather than holding one operation until generation finishes.
3. **Execute and stream:** plugin policy chooses Codex/Claude Code and delegates through protected execution brokers. Distinguish received/admitted/delivered/running/waiting/answered/cancelled/failed/outcome-unknown. Stream text/tool progress ephemerally with run/stream sequence IDs; checkpoint and final message are durable. Reconnect reads checkpoint + subsequent stream or a refreshed run snapshot. Never journal every model token.
4. **Call tools:** operation tools dispatch with the user's attenuated authority and current resource access. Harness-native shell/files/network are confined at the execution boundary as well. Tool calls carry stable effect identities and retain uncertain outcomes; replay of a transcript cannot execute them again. Permission widening requires the trusted human grant surface, even for a plugin-generated app.
5. **Delegate:** child threads get explicit context and grants, parent links, destination/account selection, durable completion/result references and attention on questions/failure/review. Helpers auto-archive after completion under the accepted policy. Workflow waits/checkpoints survive server restart without assuming a remote harness died.
6. **Control:** steer/queue/edit queued messages, stop, explicit handoff, fork and retry are ordinary operations. Cancellation distinguishes stopping local observation, requesting host cancellation and confirmed remote process termination. Reconcile a still-running remote run before launching a replacement. Provider limits persist a waiting reason and resume eligibility, using reported facts rather than fabricated quotas.
7. **Review:** thread timeline/artifacts appear in the middle; run/provider/machine/review data in right panels; sidebar lists Collections. Search resolves message/thread/artifact addresses. Attention candidates are deduplicated and capped by the shell. No workflow can hide an unresolved approval by overwriting its status with token progress.

**What the first API proof must demonstrate, not a claim of completed testing:** an authorized person admits a run; an isolated worker emits bounded stream output and requests a tool; another member cannot observe it; grant revocation stops new calls/delivery; a disconnect/restart reconstructs checkpoint and status; a child reports one result; cancellation leaves no silently duplicated effect. This exercises more of the foundation than a read-only statistics worker.

**Notes second:** provision Notes Collections and kind/format handler; list/create/get/edit/history through operations, open the middle editor and sidebar TOC, expose inspector/style panels, publish search documents/attention, sync cached offline edits, preserve conflicts and block IDs. This is where engine replacement and exact-byte/format conformance become concrete. Neither Notes nor orchestrator should need host-private tables or bespoke protocol adapters.

### A6. Coherent API shapes — options, not a selection

All options preserve the above host authority, TypeScript authoring, portable views and shared contracts. All need real OS isolation; a manifest is not a sandbox.

| Shape | Concrete form | Performance cost | Isolation and simplicity cost |
| --- | --- | --- | --- |
| **1. Manifest contributions + brokered handlers** | Manifest declares kinds, operations, Collections, shell views/panels, attention/search/settings, wakeups and service/format contracts. TS handlers receive typed context and capability RPC; host compiles indexes/catalogs on activation. | Fast discovery/routing without waking workers; bounded lazy startup and IPC per handler; long streams use separate bounded channels. More schemas to validate/cache. | Clear inspectable grants and lifecycle. Larger declaration vocabulary and duplicated metadata risk unless generated from author declarations. No direct database handles. |
| **2. Operations + subscribed views as the common model** | Most features are typed operations returning resources or view descriptors; subscriptions/deltas power sidebar, panels/search/attention. Minimal manifest declares identity, exports and permissions; domain methods provide the rest. | Fewer mechanisms but extra calls/worker wakeups for discovery and views; batch queries and cached registration snapshots become essential. A whole-view fetch per token/keystroke fails the intended budgets. | Small author mental model; effects and hidden dependencies are harder to review. Host must freeze schemas/target metadata at activation, so it still needs a declaration phase. Treating permissions or durable admission as generic replaceable operations would be invalid. |
| **3. Versioned service contracts + product compositions** | Small manifest plus independently versioned thread/workflow/provider/format/query services; forkable TS product layer composes operations and views. Default Rust engines implement public service contracts; TS replacements use the same boundary. | Can keep bulk parsing/indexing and execution scheduling close to storage; IPC amortized by batches. Additional service lookup/version negotiation and cache invalidation. | Explicit engine/client compatibility and replacement boundaries. More concepts and potential adapter layers; service contracts must not become app-specific privileges or permanently closed first-party APIs. |

A useful design-round comparison is to express **the same orchestrator admission/stream/tool/child/cancel trace and Notes edit/merge trace** in each shape, count worker crossings/bytes, then inspect grant and crash boundaries. Those counts would be estimates until measured on permitted dev/perf machines. This lane makes no timing claim.

### A7. Host-owned and not tenant-replaceable

From `new:docs/architecture-proposal.md:69–94,102–112,219–249,317–389`:

- Verified identity/session, authenticators/recovery, account-private installation/profile data; authoritative membership/grants/ownership and cross-space sharing checks. Default roles are capability sets, not plugin-overridable switches.
- Credential custody and authorized provider-account bindings, audit attribution and trusted login/grant/recovery UI. A tenant can request a grant, never approve its own widening.
- Sandbox and machine identity/grant enforcement, brokered filesystem/network/secrets, ceilings/accounting, leases/backpressure/cancellation and durable admission/receipt/checkpoint primitives. Workflow policy and provider adapters remain replaceable within these bounds.
- Canonical resource/Collection identity and owner binding, atomic write coordination, authoritative saved merges, block identity confirmation, journal/cursors/sync, version/history and recovery storage. Format engines propose transformations and can be replaced; they cannot replace the commit/authorization boundary.
- Contract validation/negotiation and transport authentication. Trusted rendering of grant/login/recovery and a safe disable/restore path remain available if a plugin breaks. Supported native component implementations ship with the client; layouts and product views remain customizable.

Conversation identity and durable visible records are protected even when the orchestrator is replaced (`new:docs/architecture-proposal.md:145–166`). This is not permission to compile the orchestrator's behavior permanently into the host.

### B3. Server journal/live and rewrite status

Old route and replay trace:

1. Generic HTTP actions, journal and live are mounted at `old:crates/server/src/lib.rs:58–68`.
2. Engine journal pages validate token, clamp page size, read one extra row, return continuation token/more (`old:crates/engine/src/lib.rs:167–219`); credential filtering is server-side. `live()` subscribes before backlog reading (`:221–247`).
3. Socket starts subscribed, validates prior cursor/epoch, catches up and emits ready (`old:crates/server/src/live.rs:101–139`). Broadcast lag invokes DB catch-up, not silent dropping (`:153–181`); rollback ends session with expired token (`:148–151`). Catch-up revalidates credentials and advances page token (`:320–365`); the inspected live code exposes credential-kind filtering, not the full proposed topic registry.
4. Incoming socket messages revalidate credentials (`:184–190`). Action tasks do not hold the live stream (`:391–397`). Notes rooms additionally have lineage and durable-save receipts (B2). A journal cursor and a room receipt acknowledge different things.

**Rewrite today:** `new:crates/client/src/lib.rs:3–4,75–116,148–169,193–209` is a reusable async **loopback HTTP preview adapter**, with validation, correlation/version/error checks, bounded buffered replies and no automatic retry. It has no durable cursor/outbox, file hydration or room sync. Dropping the future only stops waiting; it does not undo a server commit. `new:crates/core/src/validation.rs:493–541` has immutable pending-request identities and an advisory Notes base-revision check, not durable outbox persistence or a conflict engine.

`new:crates/bindings/src/lib.rs:3–5,11–47` exports synchronous JSON schema/request/GenUI validation scaffolding; it is **not a network or offline client** and has no async stream/cancel API. Generated Swift files are evidence of binding generation, not an Apple app.

`new:crates/store/src/lib.rs:1–11,353–360,403–518,594–654` provides a ported per-space journal with ordered writer, subscription, signed token validation, commit/commit-once and account-qualified receipts. `new:crates/store/src/contracts.rs:84–106` adds acting-account attribution. `new:crates/store/PORTING.md:10–24` documents DB binding, restore/witness behavior and the fact that no backend endpoint is enabled by this crate. The current preview router exposes describe/operations, not journal/live (`new:crates/server/src/api.rs:76–80`). Its preview content store is separate (`new:crates/server/src/store.rs`); possessing a journal crate does not connect Notes saves to that journal or prove content+history+journal atomicity.

Important durability limit: the port records WAL/NORMAL for ordinary commits and FULL for permanent publications (`new:crates/store/PORTING.md:15`). A generic journal commit must not be presented to clients as a power-loss-durable content-save acknowledgement without the content/history/materialization proof.

### B6. Contract generation and conformance proposal

**Starting point:** `new:crates/core/src/bin/export-contract.rs:1–28,102–121` emits JSON Schema, TypeScript declarations and operation catalog. `new:crates/core/tests/conformance.rs:11–57` and `new:packages/plugin-sdk/test/sdk.test.mjs:39–62,146–163` consume common request/GenUI/worker fixtures. This is meaningful validator parity, not sync/offline correctness. Runtime validators currently have handwritten behavior too; generated TS types alone do not validate network values.

Proposed extension: one versioned protocol definition generates Rust DTOs/validators or schema adapters, TS types/runtime validators, Swift binding-facing records and discovery/docs. Dynamic app schemas remain runtime data; installing an app does not rebuild Swift. Keep operation, journal, room, ephemeral-stream, format and GenUI versions explicit, rather than letting one package version implicitly govern all.

Add a **shared trace corpus** with initial local files/state, mocked effects, ordered input packets/user actions/crash points and expected visible state/outbox/cursor/emitted effects. Both Rust and TS runners consume identical fixtures. Swift also runs a binding-level subset to catch copying/callback/cancel issues that Rust unit tests cannot see. Expected results are independently reviewed, not generated by one implementation as the sole oracle.

Required fixture families for later verification (none executed in this lane):

1. Unicode/UTF-16/UTF-8 positions, CRLF, malformed input, unknown fields/versions and bounded message sizes; address wrong-kind/not-found equivalence and retained B1–B5 block lifecycles.
2. Overlapping catch-up/live, duplicate/out-of-order delivery, pagination with filtered topics, reconnect, expired/rollback cursor and crash between applying records and storing cursor. New filters cannot skip history silently.
3. Local write before outbox append, crash during append/send/commit/reply/receipt retirement; same ID+same input retries, changed input rejected; sign-out/account switch and revoked membership never flush another account's queue.
4. Receipts for own vs peer edits, deletion dependencies, sibling tabs, IME-gated remote updates, stale memberships and lineage replacement; repeated replay cannot create a second insertion. No safe base/partial merge preserves conflict copy.
5. Text independent/overlap changes; structured-record independent/same-field conflict; unknown fields/format/version; binary conflict dedup; setting conflict preserves both. Golden original/merged bytes where format requires lossless preservation.
6. Orchestrator admit→stream→checkpoint→disconnect→resume, tool uncertain outcome, child completion, quota wait, workflow wakeup, cancellation and late output. Bounded queues and slow consumers must yield explicit gap/reload states.
7. Multiple Apple processes or browser leader replacement, storage exhaustion and migration; deterministic fake clock/network scheduling, redacted errors and no cross-space cache leaks.

Contract drift checks, both trace runners and binding harness become release gates when implemented. Include byte/event/work budgets alongside functional outputs; fixtures cannot prove sandbox confinement or real device frame time. Measure those separately on authorized machines. Existing development timings are not performance acceptance evidence.

### B7. Client implementation options and hot boundaries

The architecture already chooses portable decision logic with platform effects. These are shapes within that decision, not alternatives to sharing Rust:

| Option | Form | Costs |
| --- | --- | --- |
| **Effect-driven state machine** | Explicit input→state/effects→result transitions; Apple and CLI supply effects; TS implements the same traces. | Most inspectable crash/cancel ordering and smallest portable dependency core. More effect plumbing, persistent-state transition design and adapter tests. Batch effects to avoid callback chatter. |
| **Core-owned async supervisor with injected adapters** | Rust task owns per-account/space sessions/outbox/sync; adapters implement files/secrets/network; UI gets batched snapshots/events. | Fewer calls and simpler app integration; harder deterministic scheduling and shutdown/reentrancy; must expose real cancellation/generation and cross-process ownership, not hide them behind async tasks. |
| **Hybrid reusable reducers plus supervisor** | Pure shared reducers/trace runner, thin async orchestration around them. | Keeps protocol decisions independently testable and batches effects, but requires discipline to stop retry/cursor policy leaking into supervisors/adapters. More layers than a minimal HTTP client. |

**Paths that must not require a UniFFI call per keystroke/frame:** native editor input/composition/caret/selection, layout/scroll/animations, backdrop sampling, pointer interactions, per-row realization and per-token text rendering. Editor integration can submit coalesced edit transactions to a background Rust owner and receive incremental change batches; never serialize/validate/copy the whole note or GenUI tree per input. Stream output coalesces by time/size and carries sequence/checkpoint metadata; cancellation/control must have a separate prompt path so batching cannot bury Stop.

UniFFI boundary facts are already recorded in `new:docs/architecture-proposal.md:237–243`: callback streams, copied byte buffers, explicit cancel IDs/methods, Apple multiple processes and version skew. Prefer authorized file handles/paths for large payloads and batch small metadata updates. Paths must be validated by the relevant host/adapter, not accepted as ambient file authority. Avoid synchronous JSON FFI helpers on UI hot paths; current bindings allocate proportional to input and are scaffolding only. Exact batch sizes/cadence and supported native widgets require implementation measurements, not a product decision by this review.

## Questions for the user

Only unresolved choices are listed, in dependency order. Sandbox mechanisms, batch sizes and storage correctness proofs are engineering validation work; they are not delegated to the user. The underlying runtime boundary and unknown-format behavior are already required.

1. **Which API authoring shape should the next round make concrete?** (1) Manifest contributions + brokered handlers: inspectable and quick to discover, more declaration types.
