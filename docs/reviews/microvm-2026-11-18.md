# Account microVM backend review

Issue [#51](https://git.kayg.org/kayg/calternal-ai/issues/51). Terms follow the
[glossary](../glossary.md). The [deployment guide](../deploy.md#choose-the-machine-sandbox-backend)
describes the opt-in offline pool mode.

## Runtime and boundaries

The [hybrid run](../measurements/sandbox-hybrid.md) measured Firecracker
1.16.1, a read-only guest root, rootless Podman with cgroup delegation, a
private data disk and host-initiated vsock. The pinned Nix shell resolves that
Firecracker version. The guest follows the measured init and launcher scripts'
device and cgroup layout. The measured pause/resume path lost vsock, so
freeze/resume applies to one Podman container and idle guests are stopped.

Every enrolled machine has a private runtime root. Within it an account
retains one sparse ext4 disk and uses one VM. The guest's one administrator
image supplies the CLI and the worker/provider toolset. The backend mounts
UUID-scoped space homes and per-thread workspaces from the account disk. The guest authenticates
control connections with a per-boot capability before parsing requests. No
guest network interface or host filesystem mount is attached. Account erasure
uses the existing durable machine message and flushes the host account disk
directory after unlink. Thread erasure syncs the guest filesystem before
acknowledgement. The process supervisor fences stale handles by guest
generation and holds an inherited lock until prior VMMs have exited.
It interrupts provider leases when a running guest is lost. Explicit resume
uses the existing provider checkpoint path.

On dev-01, `id` showed uid/gid 30033 (`claude`) with only its primary group.
`/dev/kvm` was a character device `10:232`, mode `0660`, owner `root:kvm`.
The CPU exposed `vmx`. Python `os.open("/dev/kvm", os.O_RDWR)` returned
`PermissionError: [Errno 13] Permission denied`. That prevented both KVM
ioctls. The operator can grant `claude` device access via group membership or
an ACL and then test `KVM_CREATE_VM` in a fresh login. The device permission
result is independent of whether the hypervisor handles that ioctl.

### Locked performance run

The dev-built static benchmark and checksummed guest ran on
`kayg@calternal-perf-01-backup01` under `/usr/local/bin/perf-lock.sh`.
The host control used Podman 6.1.4 with a private overlay store loaded from
the same OCI archive as the guest. The VM configuration was 2 vCPUs,
1 GiB RAM and a 4 GiB data disk.

| Host Podman metric | Samples | p50 | p95 | Max |
| --- | ---: | ---: | ---: | ---: |
| First thread through first command, ms | 10 | 588.98 | 888.66 | 888.66 |
| Second thread through first command, ms | 10 | 602.11 | 673.10 | 673.10 |
| One command, ms | 300 | 316.83 | 490.99 | 1246.09 |

At the configured cap of 20 idle accounts, the mean drop in host
`MemAvailable` was 543.62 MiB across five samples, or 27.18 MiB per account.
The run reached the imposed cap with headroom. Its raw log is
`~/calternal-ai-microvm-51/perf-retry.log` on perf-01.

The initial microVM phase exited before guest readiness. A repeat with
console capture showed that the pinned kernel had already mounted devtmpfs.
The init script tried to mount it again, got `EBUSY`, and exited as PID 1.
The guest init now checks the mount type before mounting, and the replacement
image passed its filesystem and digest checks. On perf-02 the boot then
reached Podman image import, which failed with a read-only `/var/tmp`.
Guest init now binds an account-disk directory over `/var/tmp` and reinitializes
that scratch directory on boot. This leaves the system disk immutable and
keeps image import within the account disk limit. A subsequent run using
the perf host's default temporary directory hit a host virtio-block write
error with errno 28 on `vdb`. On perf-02, `/tmp` is a 3.8 GiB tmpfs and had
620 MiB free after that run. The comparison uses a short, disk-backed
`TMPDIR` under the perf user's home so disk allocation stays out of the
idle memory samples.

The idle microVMs averaged 990.88 MiB of VMM PSS each. The respective
available-memory baselines were 3,517.85 MiB for the Podman run and

The reported population applies to that rule and those starting conditions. Prebooting one warm
guest took 34.24 seconds in one observation, including image validation and
preload. The run ended with no lane runtime fixture directories. Raw records
are in `~/calternal-ai-microvm-51/perf-disk.log` on perf-02.

The ignored comparison harness uses the previous measurements' host-observed

commands, idle account population and memory, and warm pool readiness. Build
the harness on dev-01 with `nix develop .#deploy -c cargo test --locked -j6

under `/usr/local/bin/perf-lock.sh` with the verified guest, the same

`CALTERNAL_MICROVM_TEST_CONFIG` set. The test filter is
`sandbox::microvm::measure::compare_microvm_and_podman_under_perf_lock`
with `--exact --ignored --nocapture`. The harness reports whether the
population stopped at its configured cap or the host memory reserve.

## Review gate

| Item | Review |
| --- | --- |
| 1. Shared types | Reuses `SpaceId`, account and thread UUIDs, `SandboxSpec`, `ExecRequest`, `ChunkEvent`, `ExitInfo` and the shared fsio operations. |
| 2. Dependencies | New code is in the existing machine crate and a server wiring module. Uses existing dependencies and features. |
| 3. Lock scope | One administrative runtime lock covers the daemon and inherited VMM descriptors. The account map holds a short lookup lock. A per-account async lock spans teardown, guest control and durable disk binding so that only one VM can own the disk. |
| 4. Async paths | Uses Tokio for host process, file and socket I/O. Durable renames, fsync and startup hashing run on blocking tasks. The guest opens its private device before starting its runtime. |
| 5. Reads and flushes | A warm command makes one vsock connection, one authenticated request and a bounded stream, with zero explicit host disk reads or flushes. Cold disk creation adds a format, a file flush and the fsio directory flushes. Account erase flushes one directory. |
| 6. Constant initialization | Parses operator settings once and verifies image digests at backend startup. Initializes the guest agent and its Podman storage before serving control requests. |
| 7. Bounds and retention | Guest vCPU, RAM, disk, host guest count, warm count, frame size and stream buffers are bounded. The pool has at most two blank guests and assigned guests can stop after ten idle minutes. The account disk persists until durable account erasure and a workspace until discard. |
| 8. Compatibility | Machine protocol 5 adds the guest-loss status. The server and machine upgrade together. Guest control carries the existing authoritative assignment space. |
| 9. UUID scope | Machine-local account disk names, space homes and thread workspaces use IDs throughout. |
| 10. One source of truth | The machine role supplies the verified assignment and the operator pins one guest image. The guest reuses the Podman sandbox specification and exec output types. |
| 11. Wiring | Machine run and discard enter through the existing backend trait. The durable erasure message calls the same backend. Packaging calls the guest executable. |
| 12. Reuse | Reuses machine ownership, fsio durable placement and directory sync, rootless Podman, the machine output protocol, the provider lease fence and the measured Firecracker boot layout. |
| 13. Documentation | The machine crate's public configuration and backend methods describe authorization, lifecycle and costs. See verification for the docs gate result. |
| 14. Deployment docs | Deployment covers backend selection, scoped KVM access, build inputs, digest pinning and lifecycle. Open product choices are in the [morning decisions](../morning-decisions.md#pool-microvm-networking-and-credentials-issue-51-2026-11-18). |
| 15. Formatting and size | MicroVM modules are split by VMM lifecycle, guest agent, wire, image validation and thread activation. See verification for formatting. |

## Remaining scope

Live KVM verification covers real account and sibling-thread isolation,
CPU, RAM, disk, guest loss, durability, erasure and process cleanup. The
outbound provider flow needs a verified egress policy. Shared sign-in needs
provider-specific credential-only storage across space homes. Plan-size
assignment and monthly accounting remain unimplemented. The plan decision
charges sandbox running time. The locked benchmark exercised real KVM boot and command execution. The
dev-01 conformance skip still leaves the full isolation and crash tests
pending.

## Simplification opportunities

- Share the operation-CLI mounting policy between native and guest Podman
  once the guest's provisioning contract is stable.
- Share an immutable, preloaded image store across guests to eliminate the
  per-account OCI import and its scratch space.
- Derive account admission cost and warm-pool limits from one plan capacity
  model when that contract exists.
