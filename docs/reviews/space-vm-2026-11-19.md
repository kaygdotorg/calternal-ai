# Small plugin microVM

Issue [#88](https://git.kayg.org/kayg/calternal-ai/issues/88). This lane
covers the small plugin runtime. The agent and heavy plugin runtimes have
separate placements.

## Proposed revisions

1. **Enrolled placement and vsock.** Reserve an eligible pool placement
   after admission. Its control plane carries the verified worker source
   and a small-VM selector. A capacity heartbeat advertises whether the
   operator configured that wall. The machine terminates the enrolled
   carrier and relays only the existing child protocol through its
   authenticated vsock exec connection. The guest starts the package
   using the rootless, read-only worker profile. Machine credentials and
   invocation tickets remain outside the guest. The guest has two vCPUs,
   256 MiB of memory, a bounded scratch disk and no network adapter.
2. **Cold boot entropy and readiness.** Take independent host randomness
   for the guest control capability and kernel reseed material. Carry
   them on the existing read-only boot drive. The guest init establishes
   kernel randomness before starting its trusted control agent. The
   machine requires the small-profile readiness response before starting
   a package. Node starts as a fresh process after that response.
3. **Snapshot and restore boundary.** Drain the carrier before sleep
   so the snapshot carries zero package processes, tickets, or child
   pipes. Reinitialize packages from verified source after restoring the
   guest and refreshing kernel entropy. Use the existing authenticated
   control pipe for a 32-byte host seed. A privileged guest helper mixes
   the seed, reseeds the kernel and acknowledges success. The machine
   requests readiness before starting a fresh Node process. Node seeds its
   process RNG from the reseeded guest kernel on first use.
4. **Manifest and storage fallback.** Publish a private manifest after
   fsyncing the state, memory, scratch disk and control-drive files and
   their generation directory. It records the image and metadata for each
   component. A mismatch boots cold. A consistent restore must acknowledge
   reseeding and readiness before it can dispatch. On a subsequent save,
   merge Firecracker's allocated dirty ranges into a reflink of the prior
   full image. The manifest records `full` when the filesystem cannot
   clone or enumerate sparse ranges.
5. **Failed restore and guest admission.** Bind the manifest to the space UUID
   and Firecracker release. Invalid data or an explicit load, reseed, readiness
   or Start refusal clears the saved generation and retries once as a cold boot.
   Local storage failures, transport errors and timeouts preserve the generation.
   The placement keeps the same capacity permit. The guest clears its ready
   marker before pause and recreates it only after the root helper confirms
   reseeding. Both readiness and package start check the marker. The offline
   control key is scoped to the space and kept alongside its memory image
   across restores. The enrolled carrier still issues a fresh epoch.
6. **Owner deletion and dormant retention.** Track checkpoint locations in
   the same transaction as placement, one row per space, actor and machine.
   Space deletion or erasure of an account that placed the space enqueues a
   durable remote erase. The runner stops any placement of the affected space
   on that machine before deleting its directory. Revoked or removed machines
   retain pending operator-wipe status. The preview expires dormant snapshots
   after 24 hours and sweeps every 15 minutes while the machine runs. A clean startup
   sweeps expired snapshots before accepting placements. Each space holds
   at most one published and one staged generation.
7. **Single teardown disposition.** The first terminal machine action fixes
   whether the slot saves. The dedicated small-VM sleep command can select save
   when it arrives before the carrier closes. A space waiting on an old
   machine-local placement gate gets an error within three seconds. The gate
   releases after successful VMM teardown and scratch cleanup.
8. **Checkpoint affinity.** A machine reports a saved checkpoint only after
   publication and VMM teardown. The scheduler prefers the machine with the
   newest acknowledged checkpoint. The acknowledgement transaction records
   its location and queues deletion of older copies on other machines. A
   machine with a pending erase for this space is ineligible until it confirms
   deletion, including after reconnect. An unconfigured role can sweep and
   erase this storage under the machine's inactive VMM root lock. Each sweep
   handles directory failures independently.


The warm broker still uses two SQLite queries, with one additional query
for an installation session, and zero storage flushes. Existing channel
flow control bounds the child pipe. Cold placement uses the worker lease's
existing two durable commits, with two indexed checkpoint/erasure reads for
small-VM placement. Role startup checks KVM and image integrity. Checkpoint
acknowledgement makes one conditional affinity and erasure commit before
releasing the capacity reservation. A warm call reaching the broker adds no placement reads or flushes.
A saved wake reads one bounded manifest and checks four component metadata
records and the retention timestamp. Successful sleep publication flushes four
components, the generation directory and the manifest's parent before the
pointer commit. The atomic pointer commit flushes its temporary file and
parent directory. Initial directory creation and guest disk sync have their own
durability work. Reflinks share disk extents. The fallback copies allocated
ranges using the paced file helper, with a paced full copy on filesystems
that cannot enumerate extents.

The test config uses a disposable guest image with Node 24 and
the existing rootless worker seccomp profile. Timings from dev-01 serve
only as functional deadline assertions.

## Morning decision

**How long should we keep dormant small-VM snapshots?** The lane chose 24
hours as a provisional preview setting to retain a typical overnight return
while limiting how long memory images and scratch disks accumulate. The
wall comparison found 100 full 256 MiB memory snapshots occupied 25 GiB,
before counting this product profile's scratch disks. That result explains
the need for a bound. It does not select the retention period.

For example, a person who returns to a plugin after a weekend may encounter
a cold boot. A shorter period frees disk sooner and makes cold boots more
frequent. A longer period preserves more fast wakes and keeps disk allocated
longer. Keep 24 hours for the preview while the owner decides the product
default with cold-boot and storage evidence.

After a sweep, ordinary reads remain available while the space sleeps. The
first request that needs the package waits for a fresh guest, its kernel
reseed, and package readiness, then returns the usual result. The route
has no snapshot-expiry notice. The broker allows 10 seconds for package
readiness once the carrier connects. If readiness misses that deadline,
the caller receives “enrolled item-head worker unavailable” and can retry.
Ten seconds is the readiness deadline. The existing restored-guest measurements do not
give a product cold-boot time, and that time remains unmeasured on the perf
host.

## Development verification

The live KVM fixture runs the enrolled runner and the guest worker image.
It returns four maximum-size item heads over one carrier and confirms the
Firecracker process exits after one explicit fence. The fixture uses
Firecracker 1.16.1 and the locked guest kernel. The measurement lane's
`reseed.c` supplied the kernel reseed sequence. The product reuses the
existing guest build, Node worker seccomp policy and vsock exec transport.

The idle fixture holds the machine sleep barrier while ten concurrent calls
arrive. They wait outside the wake gate and coalesce into one restore once
the machine confirms teardown.
The admitted calls return their checked heads. Excess calls receive the
existing retryable busy error. The machine fixture restores the same
generation twice and compares the kernel and Node draws. It resumes a guest
without explicit reseed and checks that readiness and Start both fail until
the root helper acknowledgement reaches the agent. This control works even
if the kernel also reseeds through VMGenID. A corrupted state file with
matching manifest metadata reaches the Firecracker load failure, forces cold
fallback and proves the old run files were removed.

The publisher fixture exits a separate process after syncing candidate
components and before committing the pointer. The previous generation
still opens. The KVM fixture also interrupts the Firecracker save before
publication and restores the previous generation to run Node. A live TLS fixture withholds
renewals without closing the TCP connection and verifies that lease loss
reaps the VMM inside five seconds. The explicit fence check has a separate
two-second bound.

Dev-01's work volume is ext4. It exercises the full-snapshot fallback.
The XFS dirty-merge path still needs a product rehearsal on a reflink
volume. No new performance figures are claimed. The snapshot status
is recorded in the manifest and in the machine's sleep event. A space
retains one published generation and at most one staging generation.
The preview keeps those files in the machine role's private directory.
Package identity stays outside the snapshot because guest package processes
are stopped before it is saved. The next Start uses the fresh approved
assignment. The maximum-result fixture still queues all four callbacks
before its first completion. It answers later requests immediately so a
second burst can exercise the existing carrier after the restore.

Use the machine's Auto backend with `--space-vm-config PATH`. Put the
digest-pinned guest image in the existing immutable image layout, with a
Node worker rootfs. Configure 256 MiB, two vCPUs, zero warm guests and omit
network policy. The role verifies the image and opens KVM at initialization.

## Simplification opportunities

Keep the guest package transport on the existing authenticated vsock exec
pipe. Reuse the same VMM ownership, control and teardown primitives for
each placement role while keeping their capacity and guest images distinct.
