## Implemented

Ten operations provide private draft save/list/get/delete and pending
queue/edit/list/cancel/confirm/submit. Account identity comes from authentication,
never an input field. Account-bound SQLite storage lives under
`appdata/accounts/<uuid>/input.db`, outside every space's files. Draft saves are
last-write-wins replacements returning server revisions. Saved drafts survive
sign-out and remain until sent or erased, under the approved count/size policy.

Pending input retains its original offline creation time and stable write request
ID. An injected clock proves the seven-day boundary: exactly seven days remains
queued, older input becomes a confirmation request and is not sent automatically.
Normal dispatch rechecks current access and reuses ordinary durable receipts.
Completed queue/submit retries read that receipt after the pending row is removed;
no second permanent response log is created. Only the captured draft revision is
erased after successful send, preserving newer composition.

The account SSE feed provides bounded invalidations, accepted bookmarks, replay,
restart and reset. It never buffers draft bodies or space identifiers. A second
client reloads currently authorized input before accepting its bookmark. Foreign
and pruned bookmarks reset. Account streams recheck sessions and use owner-local
advisory admission locks, released when the body is dropped or the process dies.

The client drains offline input into server pending submissions on reconnect and
also attempts previously queued server input. Complete outbox snapshot/restore
preserves creation time and scope; native `pending_input` / `restore_input` expose
that boundary. No merge engine is introduced. UniFFI supplies account pull/accept
and cancellation, exercised by an actual Swift XCTest. Both `calternal` and `cl`
provide drafts/pending commands through the shared adaptive output module.

Proposed defaults: 256 drafts, 256 pending submissions, 16 MiB aggregate payload,
1024 retained account invalidations, 16 space journals per connection and 128 live
connections per owner. All are positive operator-configurable startup ceilings;
existing input survives a lower ceiling and state-only age transitions do not
consume extra payload capacity. Group entitlements remain separate. Details,
wire shapes, variables and examples: [account input](../account-input.md).

HTTP membership removal, leaving and space deletion commit revocation first,
then erase that space's input from affected account stores without holding the
preview Store mutex. Account reads/streams also clean externally revoked input
before exposing it. Strict socket-publication fencing is not claimed below.

## Cost and bounds

One request opens one owner connection; schema creation happens only for a fresh
file. Each request performs a bounded distinct-space scan and current grant
checks, plus an indexed due-state/time lookup. Idle streams do not decode every
pending envelope. Admission totals use a generated payload-size column and a
covering index; they scan at most the account's bounded record count, without
loading other draft/message bodies. There is no account-wide payload scan per save.

A normal draft save reads its prior row, one budget aggregate and one prior-size
row, then upserts input, inserts/prunes invalidations and commits once. A normal
get/list adds one indexed row/page read and no durable flush. First owner use
adds directory/file creation and schema durability. Pending queue additionally
checks an existing request route and the captured draft revision. Completed
retries add one existing identifier-catalog lookup and one authorized journal
receipt read; inherited unfinished publication may add its documented recovery
flushes. The account-local transaction serializes queue/edit with this check;
it never blocks another account and is not held across normal operation dispatch.

Pending submission uses one account commit to make the envelope immutable, the
ordinary operation's existing durability path, then one account commit to remove
pending input and its unchanged draft. State-only transitions update each due
record once. A wave of old input does not repeatedly scan the queue for budgets.
Revoked input removal adds one account transaction/event per affected owner.

Account replay buffers at most 64 content-free bookmark tokens, with 1024 retained
by default. The account client uses a 64 KiB SSE buffer; the space client retains
its existing 2 MiB bound. Native delivery admits one outstanding unaccepted frame.
Outbox bounds remain 256 envelopes of at most the core 2 MiB budget. Empty account
admission files are reused, bounded by the highest configured listener ceiling.

## Unfinished and questions

- Strict revoke-versus-socket-publication linearizability and instantaneous
  cross-process revocation remain unproven. Existing delivery rechecks and
  content-free account invalidations do not supply that proof. Options: publish
  through the authority worker's serialized boundary (requires auth/transport
  changes), or generation-tagged body filtering (requires a defined publication
  boundary and still cannot recall bytes already written). No design is selected.
- Browser/Apple product integration must provide account-private durable offline
  storage, sign-out conversion of unsent edits into drafts, and local export then
  deletion after revocation. Core snapshot/restore preserves age but does not
  implement platform filesystem/Keychain/UI lifecycle policy. UI implementation
  belongs to a Claude lane; no production sign-out/export guarantee is claimed.
- General addressed agent questions, approvals, setup and secret requests still
  need the orchestrator/request owner's publication wiring. This account feed
  currently notifies drafts, pending input and their confirmation requests only;
  it does not replace the source auth installation/people/password feed.
- Atomic authorized snapshot+bookmark and retention leases, persistent item-cache
  implementations and their product adoption remain the first slice's follow-up.
- HTTP revocation erases account input after committing authority. Externally
  mutated idle account files are physically cleaned on the next input access or
  active feed poll. Immediate physical erasure through every independently opened
  auth service requires integration with that service's mutation owner.
- After an attempted send whose outcome is uncertain, input is immutable and
  cancellation refuses rather than suggesting the write was undone. Original-ID
  retry reconciles it. A separate operation for abandoning an unresolved attempt
  needs an explicit outcome/confirmation contract; no new one was selected.
- Operator ceilings are safety controls, not plan/group entitlements or a tenant
  fairness proof. No development timing is reported as a benchmark.

## Simplification opportunities

- Move protected owner database preparation and typed owner binding into a shared
  lower-level primitive when lane/simplify lands, keeping each domain's schema local.
- Factor account/space SSE parsing, cancellation and explicit native acceptance
  into one small transport helper after both protocol shapes have stable callers.
- Route general addressed requests through their existing request owner instead
  of adding another request schema or storing private bodies in journal events.
- Integrate the authority publication fence once across space and account feeds;
  avoid endpoint-specific locks that cannot serialize independent auth services.
