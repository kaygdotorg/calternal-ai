## Behavior and reuse

SSE matches the server's existing jobs transport and requires no WebSocket
upgrade or second write protocol. GET `/api/v1/live` accepts the core
`LiveSubscription` array as JSON in `subscriptions`. A connection follows 1–16
canonical distinct space UUIDs. Each optional bookmark is validated by the
existing signed `SpaceStore::position`; failure yields an explicit reset without
returning token diagnostics. No bookmark starts at the current journal head.

The reference port was read with git only: server `live.rs`, engine lines
167–247 and web `live.ts` at the existing app's `origin/dev`. The implementation
keeps subscribe-before-replay and sequence-based duplicate suppression. Existing
`SpaceStore` handles are obtained from content's journal pool, so no second
writer opens the same database. Broadcasts are bounded hints; indexed journal
pages supply every event and recover lag. Store epoch-change hints reset active
feeds. A corrupted local bookmark fails explicitly rather than silently starting
at the head.

Current session and membership are checked before delivery. Item events use one
indexed existence/kind check in the selected space database. Foreign item IDs
are filtered, and a ready bookmark covers those hidden positions. Unknown and
inaccessible spaces produce identical 404 envelopes. The router clones content
once at startup; live requests and deliveries never take the global server store
mutex. Per-space admission holds a short mutex across check-and-subscribe only.
Auth notifications reuse the existing worker, with no additional worker or
connection. A one-second fallback checks expiry and separately opened services.

The client reopens from explicitly accepted bookmarks with 250 ms–30 s backoff.
Cache invalidation completes before bookmark persistence. Reset clears derived
memory cache and stops; the platform reloads authorized state before reopening.
`BookmarkStorage` and `PersistentCache` are platform boundaries. CLI bookmarks
use inherited `calternal_fsio::write_atomic_mode`, owner-only Markdown files and
atomic replacement. Storage instances belong to one server/account and one
ordered consumer. No client merge or file replica is implemented.

`OfflineOutbox` holds immutable validated envelopes and drains in order after an
authorized connection. It uses the same stable request IDs and ordinary operation
receipts. A refusal or uncertain transport outcome retains the head and stops.
The per-account async queue lock spans a drain to prevent changes in flight;
it never serializes other accounts. Native pending-input access has a separate
lock from socket waiting. Native streams allow only one unaccepted event, so an
AsyncThrowingStream producer cannot block acceptance behind its next socket read.
Cancellation interrupts both acceptance waiting and network/backoff waiting.

## Bounds and cost

- Per connection: at most 16 pinned journals and one 64-entry replay page.
- Journal live ring: inherited 1024 entries; endpoint admission: 128 listeners
  per space. Dropping the HTTP body drops its receiver and journal handles.
- Client: 2 MiB SSE buffer; at most 16 memory bookmarks of at most 4000 bytes.
- File bookmark cache: 1024 files, each at most 4 KiB, in an exclusively owned root.
  A per-instance async mutex spans capacity checking and atomic publication.
- Item cache: 1–1024 entries, each at most 1 MiB. The default connection uses 256.
  A custom persistent cache must state its own byte/age bounds and cleanup policy.
- Offline input: at most 256 core-validated envelopes, each at most 2 MiB.
  It is ephemeral here; no indefinite server retention is silently selected.

Replay performs one indexed journal read per 64 scanned entries, zero flushes,
and one current session check, membership lookup and indexed per-space item check
per item event. A static development session needs no installation lookup.
Empty-page wakes check each followed space. Filtering can scan several pages
before yielding, with memory still bounded to one page. Ready token generation
uses the inherited proof cache/index lookup. File bookmark acceptance performs
one atomic file publication (file and directory fsync); memory acceptance has no
persistent flush. Outbox dispatch has the existing client's bounded transport
retry costs and preserves the exact request identity.

## Unfinished and questions

- Server operations to save/list/delete drafts and queue/edit/cancel/submit pending
  submissions, plus an account feed for them and addressed requests, are unbuilt.
- Retention requires a decision: configurable expiry bounds storage but can expire
  unfinished input; explicit-delete retention preserves input but needs owner
  approval for indefinite retention. Offline input after sign-out/revocation also
  needs a private retention/export policy. No option was selected by the lane.
- Offline input here is in memory. The platform must provide durable offline
  retention, account cleanup and any persistent item cache implementation. Queued
  requests are immutable; no client merge or uncertain-request rewrite is added.
- Reset is explicit and stops publication. Atomic authorized snapshot+bookmark or
  snapshot retention leases remain outside this slice; platforms must reload.
- Delivery rechecks and in-process mutation hints are exercised. A linearizable
  revoke-versus-socket-publication fence and instantaneous cross-process revocation
  are not proven; separately opened directory changes use the one-second fallback.
- Safety ceilings are currently transport constants, not plan entitlement logic or
  an operator configuration surface. No production transport/tenant proof is claimed.

## Simplification opportunities

- Reuse one bounded subscription/admission helper for jobs and journal transports;
  their authorization and keepalive loops currently remain separate.
- Share account-local owner storage/journaling once account retention is settled,
  rather than inventing an account stream by disguising an account UUID as a space.
- Remove inherited fixture aliases and obsolete ignored tests in lane/simplify;
  the new live protocol already requires canonical space UUIDs.
- Keep platform persistence behind the small storage traits. Avoid adding a file
  sync engine, merge queue or a second operation/receipt protocol to this client.
