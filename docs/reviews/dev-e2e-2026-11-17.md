### Leak paths and fixes

- The coordinator found 172 leftover thread containers and restored startup
  by removing 122 old disposable containers, lowering the account from 200
  to 39 kernel keys. The Podman release path used `stop`, which kept the
  container and its overlay. It now removes the exact runtime container
  while preserving the bind-mounted workspace and provider home. Failed starts
  use the new container ID for cleanup. The machine lock scopes the startup
  sweep to ownership labels and recognized workspace mounts in its own root.
- The machine joins in-flight starts on clean exit and revocation. Server
  shutdown fences active leases and asks connected machines to release them.
  A machine that loses contact removes local containers when it observes its
  lease TTL has elapsed. The same TTL bounds idle provider containers on a
  connected machine, with a check at the next successful poll. The sweep
  runs alongside lease renewal so a slow engine removal cannot fence the
  lease. A retry wait
  retains its logical lease and can start another container on the same machine.
- The plugin worker pool now retires and drains workers while its runtime is
  still available. It retries failed cleanup with the physical permit held.
  Worker idle retirement keeps the existing 60-second limit.
- Machine, server and conformance fixtures remove their own containers on
  unwind, after stopping any child machine. The shell gate assigns a private
  `TMPDIR` and refuses containers labelled with roots in that run. A deliberate
  leak made the gate fail. The scoped test container was then removed.

Each machine admits at most `--max-sandboxes` assigned slots, 10 by default
and 2 in this lane. This includes provider and worker slots, starts, and live
containers whose removal has yet to be confirmed. Idle provider leases keep
their logical slots, so parking cannot increase the physical limit. Mounted
workspaces and provider homes follow the existing retention policy.

### Placement ordering and PID enforcement

The native claim changed the durable state to `running` while the turn was
still acquiring its lease and before it saved the newly selected machine.
The deterministic claim regression reproduced the premature `running` view
on dev-02. The claim now uses an internal `placing` state that clients and
thread lists read as admitted. The running state and machine checkpoint are
written by the same fenced job transaction. The space journal emits the
running transition from that transaction. Cancellation, restart recovery and
active-job admission account for placing jobs. The provider test checks the
machine ID in the first running response, without polling for the ID separately.

The resource-limit fixture previously polled a cumulative `pids.events:max`
counter after launching a Node process that discarded spawn errors. A missed
poll cannot lose a kernel counter increment. The old failure did not tell us
whether the intended pressure reached the worker cgroup. The new shell probe
holds each child in that cgroup and attempts one fork at a time. It reads the
kernel counter and child exit, with the existing ten-second limit. Memory
enforcement still checks the owning cgroup's `memory.events:oom_kill` counter.
The revised test passed in the merged workspace and in five consecutive runs
of the full `plugin_workers` binary with its default test concurrency. The
guarded run left no containers. The test command was repeated five times
inside `scripts/dev-e2e/check-podman-tests.sh` under the Nix shell:
`cargo test --locked -j6 -p calternal-machine --test plugin_workers`.

The first merged workspace run reproduced an idle-sweep issue in the pool
fixture. The machine's session expired while its sync loop was blocked by
Podman removal. Moving the sweep off the sync loop preserves renewals and
the slot stays reserved until cleanup. The shutdown fixture also received
the server's Stop but its 20-second check elapsed before removal. Its
60-second bound stays below the standard 90-second local lease expiry, so it
still tests delivery of the shutdown Stop. The fixture uses completed exec
output to prove startup. A separate `running` capacity report can arrive one
full 20-second poll later and was an unreliable readiness signal for this test.
Real Podman work in that fixture uses a three-poll budget. The pool grant
fixture uses normal machine timing and verifies an authorized exec. A
separate runner test injects the idle threshold directly, checks container
removal and verifies that reassignment reads the same mounted file.

The saved-thread journal fixture also needed to account for `placing` when
injecting a wait. Its public assertions now require queued while the machine is
absent, followed by exactly the admitted, waiting and cancelled journal events.

After staging the requests merge, Cargo used stale Core and CLI artifacts for
some feature combinations and for rustdoc. The exported requests types were
present and the source hashes matched on the VM and in the worktree. Cleaning
the affected VM targets restored the build without source changes.

## Simplification opportunities

- A supported private listen address in the server would remove the lane's TCP
  relay and keep listener checks in the server lifecycle.
- A shared example of the provider job SSE envelope could drive both the browser
  adapter test and the deployment proof.
- A reproducible VM staging command that removes deleted tracked files would
  eliminate the manual cleanup after a plugin directory is renamed.
- Let the machine transport signal that its worker process has started.
  That would time worker bootstrap and operation execution separately.
