# Search and lookups, November 18, 2026

Lane `lane/search`, thread `thr_yruirs3chu`, [Forgejo issue #47](https://git.kayg.org/kayg/calternal-ai/issues/47). See the [operation and storage reference](../search.md).

The six operations share the existing admission path. Search and cross-space
prefix queries query only spaces granted `space.read` to the authenticated
account. They check the set again at delivery and recompute the entire result
if grants changed, including any continuation and coverage flag. Per-space
operations use the existing admission and delivery capability checks. The
mention query reads direct account and group grants in one directory statement.

The search projection indexes live and visible heads of opted-in Markdown kinds.
The writer and index advance in one per-space SQLite transaction. Warm reads
use one SQLite statement per space, and an existence-checked read-only handle
cache. If a read observes a pending publication intent, it uses the existing
space writer to recover it before returning an address. New saves add one
bounded projection and B-tree/FTS updates, with zero further user-file reads,
Markdown parses, transactions, or fsyncs in steady state. A space's first
initialization or rebuild uses a separate transaction and may read current
stored revision bodies. The projection stores at most 250,000 content head slots
and at most 8,192 body scalars per indexed head. The normal SQLite checkpoint
and allocation lifecycle still applies.

## Search performance

Release binaries were built on the named aarch64 dev VM for
`x86_64-unknown-linux-musl`. The dev VM bundled the musl and OpenSSL runtime
with the executables. The perf VM did not build them. Below are p95 wall-clock
HTTP round trips on `kayg@calternal-perf-01-backup01` with the
`/usr/local/bin/perf-lock.sh` lock held. Each query class has 100 warm samples
after one first request. Saves have 100 samples and no paired baseline.

| Readable corpus | Selective title | Common title | Common body | No hit | Notes update |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 space × 100,000 notes | 24.4 ms | 194.9 ms | 135.6 ms | 15.5 ms | 50.3 ms |
| 100 spaces × 100 notes | 69.0 ms | 168.9 ms | 132.5 ms | 72.1 ms | 51.5 ms |

The first selective request after restart was 30.3 ms at 100,000 notes and
278.6 ms at 100 spaces. That request used a fresh process with populated
projections. It was not an OS-cold or rebuild test. Broad queries and the
100-space cases missed the proposed 30 ms p95. The warm Notes update cases
exceeded the existing 40 ms p95 budget for this workload. Each steady-state
index update adds SQLite work to the existing commit. Total save timing
includes placement, receipts and journal work, so this run does not attribute
the difference from prior runs to the index.

## First-use rebuild performance

The probe starts with retained space authority, item IDs, paths, current heads
and version records from a stopped disposable copy. It removes the derived
search tables, Notes and tags terms and prefix indexes, and thread-list indexes.
Each case includes 32 saved thread files and no retained turns. The file stage
reads the selected Markdown and verifies the IDs in its frontmatter. It runs
the production Notes heading, tag and link projection, parses the fixture's
thread frontmatter, and stages the heads and current bytes in SQLite. The first
real server open then recreates the indexes through existing code. Task history
and installation recovery were outside the fixture.

The two stages are timed separately. The cold observations use
`sudo -n /usr/local/sbin/perf-drop-caches` before each timed stage. Warm
observations retain the page cache, pre-read the input files and sync the
fixture before measuring. Each cell is a single trial. The 1,000- and
10,000-note rows use the corrected fixture with excess Notes files, heads and
address routes removed outside the timed interval. The first pass at those
sizes left the entire Notes directory in place and inflated first-open cleanup.
The 100,000-note run and the independent three-space admission run had their
stated file counts. Peak RSS was sampled every 2 ms and excludes the kernel
page cache.

| Notes | Cache | File stage (ms) | First Notes list (ms) | Both stages serially (ms) | Open by ID, issued 5 ms later (ms) | Search after list (ms) | Peak RSS, stage / server (MiB) |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | Cold | 167.7 | 126.8 | 294 | 121.4 | 5.7 | 11.7 / 37.4 |
| 1,000 | Warm | 38.6 | 76.7 | 115 | 71.3 | 4.7 | 11.8 / 35.4 |
| 10,000 | Cold | 829.2 | 497.3 | 1,327 | 492.1 | 15.6 | 14.4 / 37.8 |
| 10,000 | Warm | 143.4 | 445.3 | 589 | 440.1 | 17.3 | 14.4 / 37.8 |
| 100,000 | Cold | 12,456 | 7,703 | 20,159 | 7,698 | 122.4 | 31.3 / 37.7 |
| 100,000 | Warm | 1,080 | 4,350 | 5,431 | 4,345 | 121.0 | 31.7 / 38.9 |

At 100,000 notes, the measured stages sum to 20.16 s cold and 5.43 s warm
before the Notes list is available if both stages run serially. Those sums
exclude process startup, which was 306 ms cold and 74 ms warm. The same-space
ID read completed alongside first list. Tags and Threads were available after
the first open. The next tag list took about 22 ms and the first thread list
took 3.7 ms cold or 2.2 ms warm. Search was ready on its next request. The
current synchronous first-open path therefore blocks same-space list and ID
reads for the projection rebuild.

The admission trial used one already-open space serving a read and a save.
After launching 0, 1 or 2 simultaneous rebuilds of other 10,000-note spaces,
the probe waited 25 ms and issued both healthy-space requests. The actual
foreground executor has two read threads and a separate write pool.

| Rebuilds active when probed | Rebuilding-space first lists | Healthy ID read | Healthy Notes save | Peak server RSS |
| ---: | --- | ---: | ---: | ---: |
| 0 | — | 1.3 ms | 50.3 ms | 37.3 MiB |
| 1 | 432.9 ms | 2.0 ms | 51.7 ms | 42.0 MiB |
| 2 | 674.1 ms and 673.6 ms | 648.1 ms | 85.5 ms | 44.0 MiB |

One synchronous rebuild left a foreground reader available in this workload.
Two occupied both read threads and queued a request to a different space.
These observations establish the executor contention in the current topology.
A production background concurrency setting needs its own repeated load test.

To make first open usable during a rebuild:

- Keep the stable UUID-to-file route and minimal ordered head metadata in the
  retained core if the product requires a complete first list and ID opens
  before derived data is ready. If ordered headers are also discarded, the
  first list needs an explicitly partial contract while files are enumerated.
- Schedule bounded per-space rebuilds outside foreground admission and the
  ordinary space lock. A separate worker budget should bound active spaces,
  memory and disk pressure. Start qualification with one background rebuild
  and measure both foreground reads and saves before increasing concurrency.
- Invalidate the derived generation on upgrade and expose rebuild status to
  search clients. Publish the new projection atomically. Reconcile saves that committed during the scan before
  publication, recheck current access, and cancel a rebuild when its space is
  erased. The existing hot path keeps the same accounting for receipts and
  durable revision writes.
- Serve excerpts only for the globally selected page and add cheaper title and
  body candidate paths before treating the measured cross-space search latency
  as suitable for keystrokes.

## Remaining decisions and limits

Ranking refinements, recents and frecency, and typed filter tokens are recorded
in [morning decisions](../morning-decisions.md#search-and-palette-issue-47) with
options and cost. The current tie-break is UUID within match tier to support
reproducible pagination. Title-only one-edit fallback has no body dictionary.

Externally provisioned skills use bounded descriptor-relative reads because
there is no indexed managed skill write path. The preview ships no per-space
skill files. The listing accepts single-line descriptions and
matching directory names from the [Agent Skills specification](https://agentskills.io/specification).
The real web client's wiring and container-backed gates are handled in the
parallel UI and coordinator lanes.

- If managed skills gain a write operation, project descriptors in that
