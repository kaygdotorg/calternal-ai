## Decided in round 28 (not questions)

| | Decision |
| --- | --- |
| G1 | A plugin update that changes a kind follows fixed rules, never migration code: an added field is automatic; a rename is declared with a `was` line, which stays in the kind file as its history; a removed field's values stay in the files, unshown; a retype is refused unless every value converts |
| G2 | When a person changed a plugin's collection or sidebar and the plugin updates it, the person's version stays and the plugin's new one is offered; Reset is always there |
| G3 | A person may add their own fields to any kind in a space; they survive updates, work in collections and formulas, and the plugin ignores them |
| G4 | A harness may start other processes inside the run's sandbox; Stop ends them all; hours and memory count the whole family |

## Step 2: files, the format and writes

**2.1 A broken item (a missing required field, a wrong type).** *Inherited.*
Reading is lenient and nothing is rewritten on read; a file whose
frontmatter does not parse is shown but cannot be changed until fixed
(0066 "The index"); unknown keys and comments survive edits, and anything
unsupported is "kept exactly as typed; nothing lost; shown as is" (0068);
Money shows such a record as a **Problem** that keeps the source text and
lets only the totals depending on it wait (`docs/money/format.md`, "When
something is wrong: Problems"). *For the build:* every kind gets a
server-made "Problems" collection listing items that break their kind, with
the reason; a free change to such an item is refused until it is fixed.

**2.2 Free add, change and remove against operations-only kinds.** *Question.*

> **What:** every kind gets add, change and remove for free (round 25), but a
> free "change" on a chat message or a reconciled transaction is exactly what
> "operations only" forbids.
> **Why now:** it decides the format's `operations` key and what the CLI, API
> and MCP offer for every kind.
> **Example:** `calternal transactions change <id> --amount 0` on a cleared
> transaction.
> **Options:** (a) **one operations list per kind**: the built-in `add`,
> `change`, `remove` are present unless removed or given a condition
> (`change: when not cleared`); one-line declared operations (today's
> `actions`) and coded operations by name sit in the same list; an
> operations-only kind gets no built-ins unless it lists them. Cost: one key
> more in every operations-only kind. (b) Built-ins always exist; operations-
> only kinds refuse them at run time. Cost: the CLI and MCP advertise
> operations that always fail.
> **Recommendation:** (a). One list says everything a kind can do, and the
> `actions` key merges into it.

**2.3 Rules beyond types ("ends after starts", "amount is not zero").** *Question.*

> **What:** a kind may need checks no field type expresses.
> **Why now:** free writes, merges and outside edits all need one place to
> check.
> **Example:** an event with `ends` before `starts`, written by hand over
> WebDAV.
> **Options:** (a) **`checks:` lines in the kind file, in the formula
> language** (`ends >= starts`, `amount != 0`), with the same limits as
> formulas; a write that fails a check is refused with the line as the
> message; a hand edit that fails is a Problem (2.1); **a field-by-field
> merge (S2) whose result fails a check keeps both versions**. Cost: checks
> run on every write. (b) Checks only in coded operations. Cost: free writes
> and merges cannot keep a kind valid.
> **Recommendation:** (a).

**2.4 Who may change files under `.calternal/` from outside.** *Question.*

> **What:** kinds, collections, sidebars and plugin files live in the
> space's `.calternal/`. Over WebDAV a member could flip a kind from
> `operations` to `outside`, or point its folder at another kind's files.
> **Why now:** the operations-only switch is only as strong as this.
> **Example:** a member edits `.calternal/kinds/chats.md` in a text editor.
> **Options:** (a) **`.calternal/` is not in the WebDAV mount and never handed
> to an agent; kinds and collections change only through the app's editors
> and installs**, checked like any operation (a member may add a
> description-only kind, round 22; changing an installed plugin's kind is
> refused; `editable` can never change after create, round 17). Cost:
> power users cannot hand-edit their kind files. (b) Read-only in the mount.
> Cost: people see files they cannot change. (c) Editable, re-checked on
> change. Cost: every outside edit of a kind file needs the full install
> check.
> **Recommendation:** (b): visible and readable, as "Markdown everywhere"
> asks, changed only through the app.

**2.5 Two plugins with the same kind ID or folder.** *Decided and for the
build.* A second kind with an existing ID fails at install (revision 3's
can't-list, files section doubt 6). *For the build:* a folder that already
holds files is offered for adoption (its Markdown files become items of the
new kind, Problems where they do not fit) or the installer asks for another
folder name.

**2.6 Item templates, attachments and items that are folders.** *Question,
with one part inherited.*

> **What:** a kind may want a starting body for new items; an item may hold
> attachments; the skills box made "an item is a folder" necessary.
> **Inherited:** a file's type is detected from its content, never its
> extension; attachments go to Documents or Photos by type (0028).
> **Why now:** it fixes how `add` creates an item and where a `file` field
> points.
> **Example:** a Notes template "Meeting"; a transaction's receipt photo.
> **Options:** (a) **a kind may name a `template:` file in its plugin; an
> item may be `file` (default) or `folder with <main file>`; a `file` field
> links to a file stored by 0028's rule (Photos or Documents), never a copy
> in the item.** Cost: attachments live away from their item. (b)
> Attachments inside the item's folder. Cost: departs from 0028, and every
> item becomes a folder.
> **Recommendation:** (a), keeping 0028.

**2.7 The format's own version.** *For the build.* Every kind, collection,
sidebar and `plugin.md` carries `format: 1`; the function list is part of
the format version. A server refuses at install a file whose format or
functions it does not know, naming them ("this plugin needs format 2;
update the server"); it never half-reads a newer file.

**2.8 Item names, identity and undo.** *Inherited.* Stable IDs, readable
names as labels (0056); portable names and clash rules (0043); undo undoes
only your own changes (0022) and keeps files in Trash (0073).

## Step 2b: questions and formulas

**2b.1 Search.** *Inherited, with one question.* FTS5, a trigram index for
titles, bigrams for scripts without spaces, a budget per search (0031);
ranking without corpus-wide statistics (A17).

> **What:** which fields of a kind are searched, and with what weight.
> **Why now:** the index is built in step 2b.
> **Example:** searching "Lisbon" should rank a trip's title above a mail
> body that mentions it.
> **Options:** (a) **a `search:` line in the kind file listing fields in
> order of weight (`search: title, tags, body`); default title then body;
> snippets come from the first matching field.** Cost: one more line per
> kind. (b) Every text field equally. Cost: noisy results.
> **Recommendation:** (a).

**2b.2 What a device holds of a large space, and what formulas show.**
*Inherited and decided.* Small data syncs fully; photos, large files and
older mail bodies download when opened or pinned; thumbnails stay on every
device; a warm page of 100 in a 100,000-item index takes under 50 ms (0046).
Formulas and totals are computed on the device, marked not yet confirmed
(S3, round 26). *For the build:* a total over items the device does not
fully hold uses the server's last confirmed value plus local changes, and
says "not yet confirmed"; metadata of 100,000 photos syncs, their files do
not.

## Step 3: spaces, rights and links

**3.1 Roles and rights per kind or collection.** *Inherited, with one
question.* Roles are capability sets stored in `auth.db`; checks ask for a
capability, never a role name (0058); every member reads every file within
their role (T2).

> **What:** whether a kind can require a higher role than editor to change
> its items.
> **Why now:** the one check needs to know what to ask for.
> **Example:** in the family space, only managers may change Money.
> **Options:** (a) **a kind may say `change: manager` (default `editor`);
> nothing per collection, since collections grant nothing.** Cost: one
> optional key. (b) No per-kind rights. Cost: Money in a shared space is
> editable by every editor.
> **Recommendation:** (a).

**3.2 Changes a device made offline.** *Inherited and decided.* Every
change, online or replayed from a device's outbox, goes through the same
route and the one check (0044, 0047; §5 of the proposal). *For the build:*
the server re-checks rights, the kind, its checks and operations-only on
every replayed change; a refused change is shown to the person as not
applied, with their text kept. A modified client gains nothing, because the
device's own checks are only for the interface.

**3.3 Links into another space.** *Partly decided (S4), partly a question.*
A reader without access to the target sees what 0040 shows for a link that
leads nowhere: the link's words with a lock icon and "you have no access",
never the target's title.

> **What:** who rewrites a link when a note is renamed in a space whose
> linking files the renamer cannot write.
> **Why now:** D2 says the server rewrites the link in every file; S4 allows
> links across spaces.
> **Example:** Sam renames a note in "Lisbon trip"; Ana's personal journal
> links to it.
> **Options:** (a) **the server rewrites the link destination in every
> linking file in every space, never its words, recorded in that file's
> history as "link updated after a rename"** (D2 applied across spaces).
> Cost: a server write in a space the renamer has no right to. (b) Only in
> spaces the renamer can write; elsewhere the link resolves by ID
> (0056) and shows the new name. Cost: the file on disk keeps the old path.
> **Recommendation:** (a): links follow every rename, as decided, and only
> the destination changes.

## Step 4: running code

**4.1 The whole surface `operations.ts` sees.** *For the build, shown so its
size can be judged.* Limits are operator defaults unless marked fixed.

| Call | One line | Bound (proposed) |
| --- | --- | --- |
| `s.query(q)` | A collection-style query, with totals | 200 rows a page; cursor for more |
| `s.read(item)` | One item's fields, body and records | 32 MiB per item |
| `s.write([…])` | A list of add, change, remove and append changes that commit together | 1,000 changes, 16 MiB a write |
| `s.fetch(req, { secret })` | An HTTP request to a declared destination, the secret attached by the server | 32 MiB reply, 60 s |
| `s.connect(name)` | The open IMAP or SMTP connection the server holds | 1 per declared server |
| `s.notify(people, { item, text })` | A push to people who may read the item; muted people are skipped | 100 recipients a call |
| `s.job(program, items)` | Start a background job | 10,000 items a job |
| `s.run(program, { scope, targets })` | Start an agent run (harness plugins) | per the run's quota |
| `s.call("plugin.op", input)` | A listed operation of another plugin | depth 8 (fixed) |
| `s.state` | This person's state for this plugin | 64 KiB |
| `s.cache` | The plugin's rebuildable store (D3) | per-plugin quota |
| `s.me`, `s.space`, `s.event` | Who is acting, where, and why this code started | — |

Events an operation may listen to: `on.call`, `on.time(field)`,
`on.schedule(repeat)`, `on.change(kind or collection)`, `on.outside(name)`
(an API call with a person's token), `on.connection(name)` (data on a
server-held connection). Twelve calls and six events.

**4.2 Event delivery.** *For the build.* Events are delivered at least once,
each with a key; a write made with the same key is a replay. A plugin's own
writes do not fire its own `on.change`. Changes are coalesced per item, so
a burst of edits is one event.

**4.3 Declared automations without code.** *Inherited, with one question.*
The old app's automations are editable notes with When/If/Do, any/all
conditions, chat-based creation, manual controls, run details and repair
(`docs/inheritance-audit.md`); a run uses the authority of the person who
made it (open-questions, 2026-11-19). In the new format they map exactly:
**When** is an event, **If** a condition in the formula language, **Do**
one operation from a kind's operations list.

> **What:** whether automations are a server feature or a plugin.
> **Why now:** round 27's test (useful to two unrelated apps, describable
> without naming one) is passed, but nothing new is needed in the server.
> **Example:** "When a task is done, if it has a project, add a note to the
> project."
> **Options:** (a) **an official plugin `calternal-automations`, whose
> `automations` kind holds When/If/Do items and whose one coded operation
> listens to the events and calls the named operation as the automation's
> maker**. Cost: one more plugin, and its process when automations exist.
> (b) Built into the server. Cost: an engine in the server that a plugin
> could be.
> **Recommendation:** (a), since every part is already a server primitive.

## Step 6: agent runs

**6.1 Processes on the person's own machine.** *Question* (G4 settles the
sandbox).

> **What:** a "direct, full access" run on the person's own machine (personal
> space only) has no sandbox; a harness may start processes that detach.
> **Why now:** Stop and the 24-hour rule must end the whole run there too.
> **Example:** Codex starts a dev server that keeps running after its task.
> **Options:** (a) **the machine's runner starts the harness in its own
> process group or cgroup (job object on Windows); Stop and the 24-hour rule
> end the whole group; hours count the group**. Cost: a process that
> deliberately escapes the group survives. (b) Stop ends only the harness
> process. Cost: children keep running.
> **Recommendation:** (a).

Agent rules for runs are in [agent-rules-research-2026-11-24.md](agent-rules-research-2026-11-24.md).

## Step 8: plugins, calls and shipping

**8.1 How an author tests and ships.** *Decided, with one question.* Tests run
against the real host binary in test mode (revision 2 §4.8, never a second fake host);
`calternal check` runs the installer's validator and prints the install
sentence (A22); authoring skills ship with the SDK (A22); versions are
semantic in `plugin.md`, and kind changes follow G1.

> **What:** where plugins are published, and how the server's pinned list
> relates.
> **Why now:** the operator reviews nothing (I1), so the source decides what
> an Owner can install.
> **Example:** a stranger publishes `acme-habits`; can your Owner install it?
> **Options:** (a) **any Git URL or file, installed by a space's Owner with
> the install sheet, plus an optional list the operator pins as
> "suggested"**. Cost: no central review. (b) Only from a gallery the
> project runs, signed. Cost: someone runs and reviews the gallery. (c) Only
> from the operator's pinned list. Cost: contradicts "the operator cannot
> audit every plugin" (I1).
> **Recommendation:** (a), with official plugins marked (I1).

**8.2 A removed plugin's files.** *For the build.* Items stay (decided); the
plugin's collections and sidebars leave `.calternal/` unless a person
changed them (G2), in which case the changed copy stays with a note that its
plugin is gone.
