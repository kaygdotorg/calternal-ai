# calternal-ai: architecture review

Date: 2026-11-16

Reviewed: [architecture-proposal.md](architecture-proposal.md), against existing Calternal `origin/dev` at `ea57b84b9` (`ARCHITECTURE.md`, `perf/budgets.json`, ADRs 0005, 0009, 0010, 0011, 0031, 0043, 0044, 0045, 0047, 0048, 0072, sharing decisions #409), the UniFFI documentation, and the published licenses of the cited sources. The server host choice is covered separately in [server-host-assessment.md](server-host-assessment.md).

Nothing here was measured. Line numbers in the original findings are historical review anchors; use section names after subsequent additions.

19 findings are fixed in the proposal; 8 remain open, covering engineering proofs and deferred release policy; these are not eight unanswered product questions.

## Follow-up decisions and evidence, 2026-11-16

| Topic | Current resolution | Remaining work |
| --- | --- | --- |
| Fork depth | User accepted immediate product-layer customization and incremental compatible engine contracts, starting with Notes. All product behavior outside the foundation remains replaceable. | Specify and validate engine contracts; no unresolved fork-policy choice. |
| Account recovery | User explicitly chose administrator-assisted recovery because the system is not E2EE. This supersedes the earlier no-admin-reset rule. | Protected identity verification, authenticator enrollment/reset, session revocation, notification and audit procedure. |
| External sharing | User accepted one-time scoped permission, without repeated prompts within the grant. | Validate effective authority and injection containment. Revocation cannot recall received copies. |
| Browser offline editing | Source inspection confirms existing cached-note offline reopening/editing/reconnect and offline preferences. Reuse these paths. | Adapt resource/account/space namespacing and rerun tests; arbitrary offline plugin operations and uncached data are not established. |
| Version support window | User approved capability negotiation now and deferring the exact duration/version range to native release planning. | Negotiate capabilities now; set compatibility commitments before native release. |

The supported-device list and percentile acceptance budgets must be specified before performance testing. The 120 Hz target is settled. Findings below retain their original problem descriptions; the status and resolution columns reflect the latest decisions.

## Findings

| # | Severity | Status | Finding | Proposal | What was done |
| --- | --- | --- | --- | --- | --- |
| 1 | high | open | **Provider login material may be readable by model-directed tools.** §6 relied on 'an isolated harness environment' to protect provider credentials. Codex and Claude Code can run model-directed shell commands, and their login material sits in the harness environment. Whether those commands can read it is untested per CLI, account type and sandbox mode; if they can, prompt injection or any participant directing a shared cal could extract the account holder's token. | §6, line 258 | §6 now states this as a threat to test, requires credentials to be unreadable by model-directed tools, and gates binding an account to a shared cal (any use on behalf of others) until a protected mechanism is validated for that provider and account type. No warning-only path. §13 carries the validation. |
| 2 | high | open | **Space ownership changes the existing per-person storage and sync model.** §11 proposed reusing action/sync contracts, identities and sharing. Existing Calternal has one Home, journal and search index per person (ADR 0044, ADR 0031) and shares stay in the owner's Home (#409). Spaces change the storage root, journal partitioning, cursors and revocation behavior. Five accepted ADRs are contradicted without being named. | §7, line 280 | §7 states the partitioning redesign; §11 adds a table of superseded decisions (ADR 0009, 0010, 0044/0031, 0048, 0072, #409); §13 adds the validation. The partitioned sync design itself is not done. |
| 3 | high | open | **Forking first-party apps conflicted with reusing compiled Rust code.** §4 promises a 'make this my own' fork without forking the host; §5 says compiled-in Rust modules need a host release; §11 reuses compiled Notes/search code. | §4, line 97 | User accepted immediate product-layer forks and incremental compatible engine contracts starting with Notes. Every product layer remains replaceable through plugin API except foundation. The policy is settled; engine contract design and validation remain open. |
| 4 | high | open | **Performance was a requirement without a gate plan.** §1 said 'performance is a release requirement' and §11 listed areas to budget, but there was no frame-rate target, no measurement definitions, no device matrix, no baseline, and nothing tying isolation and plugin load to UI responsiveness. The user's requirement is 120 fps interaction with everything measured. | §11, line 346 | §1 states the 120 Hz target as a design and release gate. §11 adds a performance gate plan: design rules (nothing expensive on a UI thread, coarse batched operations, provisional optimistic UI that never shows unacknowledged writes as confirmed, end-to-end tracing), the measurements as distributions, datasets, device matrix with recorded conditions, regression baseline against existing Calternal (ADR 0005, perf/budgets.json), and the same traces under plugin/cal load. §12 step 1 sets up the harness first. The supported-device list and percentile budgets must be specified before testing; none are invented here. |
| 5 | high | fixed | **Authority was undefined when several people, a shared cal or a space plugin are involved.** §1 said a thread's authority comes from 'the acting person and explicit grants'. With shared cals, manager-delegated cal authority (§2) and space-installed backends invoked by members, that left confused-deputy paths: a low-privilege participant steering a privileged cal, and a space's plugin acting with a member's authority in the member's other spaces. | §6, line 237 | Added §6 'Effective authority': requester ∩ cal grants ∩ plugin installation scope, re-checked at dispatch; standing delegated authority is bound to its grantor and context; shared resources keep the owning space's plugin as write authority. |
| 6 | high | fixed | **Cross-space surfaces conflicted with space-replaceable plugins.** Activity and the palette aggregate across all of a person's spaces (§3) but were listed as plugins a space can replace (§4). A space's replacement would have seen other spaces' items. Personal layout and review state also had no defined home; 'the user's space' was undefined under the one-space model. | §4, line 93 | §4 now defines deployment, space and personal scopes; aggregating surfaces run at personal scope and spaces contribute only through contracts. Account-local state lives in a protected account profile (not a space, not shareable). Personal plugin installs pin the version their owner activated. |
| 7 | high | fixed | **Sync, journal and history looked tenant-replaceable.** 'Files, synchronization, history' sat in the first-party plugin table with no scope while §4 let spaces replace 'permitted services'. Released clients carry sync logic and a space's history is its durability guarantee; neither can follow tenant code. | §4, line 77 | Journal, sync protocol and history storage added to the protected list; the plugin table gained a 'Who can replace it' column. File and merge handlers remain space-extensible, consistent with the accepted space-owned list. |
| 8 | high | fixed | **Harness edits could be lost or overwrite newer content.** §7 said harness file tools work in isolated areas and changes pass through the action path, without saying how. Copying files in is an unchecked read; write-back without a base version is an overwrite; a crash between edit and write-back loses the work. | §7, line 284 | §7 now sets three rules: authority checked at materialization, write-back as a based action merged per ADR 0045, working area retained until written back or discarded. Validation added in §13. |
| 9 | high | fixed | **Version pinning of running work had no limits.** §4 pinned running work to its implementation/configuration version 'until a deliberate handoff'. Read literally, revocation, plugin disable, a security block or a format migration would not reach running work, and old versions would be retained without bound. | §4, line 91 | §4 now states the pin never covers authority, that grants are re-checked per operation, and that security blocks and unreadable format migrations end the pin at a safe point. |
| 10 | high | fixed | **Browser Wasm core was required but disputed.** §5 and §12 made a browser Wasm build of the Rust core part of the first proof. The user disputes this on responsiveness grounds. Dropping it without replacement would leave two unrelated sync clients. | §5, line 181 | §5 rewritten per user steering: Rust core for Apple (UniFFI), CLI and MCP as in ADR 0072; browser is TypeScript on generated contract types and the same conformance fixtures; server is the only sync authority; no Wasm in the initial scope, stated as a preference, not a measurement. §12 and §13 updated; end-to-end responsiveness and call batching are gates. |
| 11 | medium | open | **No client/server version-skew policy.** App Store clients lag the hosted server and self-hosted servers lag the App Store client, so skew runs both ways. §13 mentioned API versioning only generally. | §5, line 199 | §5 requires capability negotiation and a clear failure outside the window. The window length is open (§13 item 5). |
| 12 | medium | open | **Isolation boundary strength and self-host constraints unstated.** §5 says 'operating-system isolation' without a threat model. Public signup plus generated server-side code and shell-capable harnesses means hostile co-tenants. The existing server ships as a rootless podman image (ADR 0009), which restricts nested sandboxing. Harness-native tools bypass operation dispatch entirely. | §5, line 148 | §4 and §5 state the threat model, default-deny egress, that the sandbox rather than the dispatcher confines harness tools, and that hosted and self-hosted may need different mechanisms. Mechanism choice remains a validation (§13, and the host assessment). |
| 13 | medium | open | **Approve-for-me plus untrusted content enables injected actions.** A thread is a full app operator with approve-for-me by default and reads shared notes, web pages and mail. Injected text could direct it to install code, share or exfiltrate. | §6, line 249 | Effective-authority intersection, scoped grants and structural controls are specified. User approved one-time scoped permission for external sharing with no repeated prompts. Policy is settled; prompt-injection/capability containment still needs validation, and revocation cannot recall received copies. |
| 14 | medium | fixed | **Loss of every authenticator has no defined outcome.** §2 has any-passkey plus OIDC and no recovery category; §4 listed 'recovery surfaces' without a path. An account with no authenticator left is unrecoverable, and a space it solely owns has no owner. Administrator reset would contradict §2. | §2, line 28 | User resolved policy on 2026-11-16: contact an administrator after losing all sign-in methods. Proposal defines protected recovery of the same account, verification, fresh authenticator enrollment, session revocation and audit; exact operational procedure remains an implementation task. |
| 15 | medium | open | **Provider terms and CLI distribution unverified.** The product depends on subscription logins used server-side, shared-cal use of one person's account, optional pooling, and installing Claude Code (not open-source licensed) in deployments. No terms were checked in the proposal. No prohibition has been established. | §13, line 423 | Recorded as a release gate in §13 with the terms consulted and date to be recorded per provider and account type. |
| 16 | medium | fixed | **UniFFI cancellation and payload limits were understated.** UniFFI's documentation says cancellation is not directly supported; there is no stream type; byte buffers are copied. Apple extensions run the core in several processes under tight memory limits. | §5, line 195 | §5 'Native bindings' states these limits, requires explicit cancel methods, path/handle transfer for large content, cross-process locking and local-state migration. |
| 17 | medium | fixed | **Multi-tab browser clients would race on one outbox.** Each tab running its own sync client against shared origin storage races on cursor and outbox. | §5, line 189 | §5 requires a single owning context (SharedWorker or leader tab). |
| 18 | medium | fixed | **Tenant-defined resource kinds cannot merge on native clients.** ADR 0048 shares Rust format plugins between server and clients. Tenant plugins are server-side TypeScript, so native clients cannot run their format or merge logic; the proposal implied uniform client behavior. | §5, line 205 | §5 states opaque handling and server-side merge for tenant kinds and replaced engines, following ADR 0048's recommended answer. |
| 19 | medium | fixed | **Trusted surfaces could be driven by a thread.** §6 makes UI control operations public so a thread can operate the app. Nothing excluded the trusted grant/login surfaces, so a thread could approve its own request. | §4, line 76 | §4 excludes trusted surfaces from thread UI operations and from context capture. |
| 20 | medium | fixed | **Authority and runtime records were assumed file-backed; restore could resurrect revoked grants.** §13 listed 'file-backed authoritative runtime/security records'. File-over-app is a content decision; grants and admission records need transactions. With several stores, restoring an older authority store beside newer content brings back revoked shares. | §7, line 278 | §7 scopes file-over-app to content, requires transactional exportable authority storage, and requires backup/restore to treat all stores as one set. §13 reworded. |
| 21 | medium | fixed | **Durable execution states and restart behavior incomplete.** §9 listed six states with no cancelled, waiting-on-person or outcome-unknown state although item 4 depends on the last. Token streams versus durable records were not distinguished. Host upgrades kill harness processes. Harness session files hold conversation content outside the stated storage rules. | §9, line 307 | §9 items 2, 5 and 6 and §6 (harness session files) updated. |
| 22 | medium | fixed | **Lazy plugin start conflicts with the palette latency gate.** §5 requires lazy, non-resident plugins; §11 keeps the 50 ms first-result gate; §4 makes search providers tenant plugins. A cold tenant provider cannot meet the gate, and the manifest had no activation triggers. | §5, line 146 | §5 separates built-in providers (in budget) from tenant providers (merged under a deadline); §6 adds activation triggers and private-state declarations; §11 notes the gates must be re-measured across spaces and isolation. |
| 23 | medium | fixed | **Operator privacy claim did not cover operator-deployed code.** §2 says administrators have no application-level route to private data, while deployment administration installs trusted modules and default plugins that process every space's data. | §2, line 27 | §2 clarifies the claim is 'no in-app route', not protection from the operator's code. |
| 24 | low | fixed | **Order of work builds a large first-experience set before validation.** Step 5 requires authentication, spaces, Activity, shared conversations, palette, memory, voice, feedback and import before step 6 validates crash recovery and revocation. Accepted scope is not narrowed here; the risk is that isolation or durability findings in step 6 force rework across all of them. | §12, line 394 | Step 3 covers hostile-plugin and credential-read tests. Step 5 now requires each increment to pass applicable performance, isolation and recovery gates before expanding, with the first plugin-under-load gate before the broader feature set. |
| 25 | low | fixed | **License facts for cited sources were assumed, not stated.** §11 and §13 mention license-compatible reuse without facts. Checked 2026-11-16 via the GitHub API: bb-lite, pi-mono, t3code, hermes-agent, CLIProxyAPI MIT; Codex Apache-2.0; UniFFI MPL-2.0; Honcho AGPL-3.0. Local bb plugin checkouts have no license file. | §11, line 386 | §11 records the licenses; §13 adds gates for App Store distribution of the AGPLv3 client, plugin SDK terms and bb plugin reuse. AGPLv3 itself is not reopened. |
| 26 | low | fixed | **§13 claimed no product decisions were outstanding.** §13 said no product-choice questionnaire blocks the proposal. Review found five decisions that are the user's. | §13, line 428 | §13 restructured into engineering validations, release gates and open product decisions, each with a working default. |

## Checked and left as is

- The single-sidebar navigation contract (§3) matches the supplied sketch: one left sidebar with app heading, Activity, app-specific elements and footer; a main card; an optional right chat pane.
- The proposal's statement that UniFFI ships no Wasm bindings generator matches the UniFFI documentation.
- Every external link in §14 resolved on 2026-11-16. The Hermes pull request cited is still open, so it is a lead, not a shipped implementation.
- `crates/client` from ADR 0072 does not exist on `origin/dev`; the shared client core is new work.
