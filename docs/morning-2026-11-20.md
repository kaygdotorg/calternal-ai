## Questions for you

Each says what it is, why now, an example, what each choice costs, and the recommendation.

### 1. May an agent search or list a space?

- **What:** today an agent with Full access can list and search everything in the space it runs in. Revision 14 gives each agent run only the items it was handed (references), with no discovery.
- **Why now:** it is the one interim default that removes something working today, so it blocks moving the orchestrator onto the plugin contract.
- **Example:** "find my notes about the lease and summarise them" works today; under references-only the agent can read only notes you attached.
- **Choices:** (a) references only: safest, agents lose "find"; (b) search allowed per run with a visible permission on the send: keeps "find", every run that uses it is labelled; (c) as today for Full access.
- **Recommendation:** (b). It keeps the feature and makes the grant explicit.

### 2. May the official provider program read its own login inside one person's sandbox?

- **What:** Claude Code and Codex subscription logins cannot be brokered: the program needs the login file itself. Measured overnight.
- **Why now:** revision 14's rule "a plugin never holds a credential" cannot hold for these two.
- **Example:** your Claude Code sign-in sits in your agent VM on your machine; the Claude Code program reads it; nothing else in the VM is supposed to.
- **Choices:** (a) allow it for a verified provider program, one person's sandbox, on that person's machine or their own cloud VM: works, the login is exposed to whatever the agent runs there; (b) API keys only through the broker: safe, subscriptions stop working.
- **Recommendation:** (a), never in a shared space, labelled in the machine settings.

### 3. The list index: same transaction as the save, or just after?

- **What:** the sealed text says a list's index updates in the same database transaction as a save. Measured, that misses the 40 ms save gate once a note sits in several lists.
- **Why now:** the engine is built and held; nothing list-shaped in v2 can ship until this is chosen.
- **Example:** saving an 8 KiB note that is in 16 collections: 55 ms p95 in the sealed design, 32 ms with a background update. With the background update the list trails the save by about 2 ms (p95), up to about 20 ms (p99 at 32 collections), and shows "loading" with no count for that instant.
- **Choices:** (a) keep the sealed design and relax the gate; (b) background update (the only option under 40 ms in all eight measured cases), needs power-cut and backlog tests first; (c) packed same-transaction tables: 44 to 55 ms, still over.
- **Recommendation:** (b), as a numbered change to the sealed text.

### 4. Seal the contract text separately from the verifier program?

- **What:** from 13.8 the Python verifier is normative: a description conforms only if the verifier accepts it. Most late review findings are bugs in that program, not in the contract.
- **Why now:** revision 14 has had eleven rounds and sits at four or five findings a round; about three of every four are in the hand-written verifier, and each fix opens a neighbouring case. The host lane's assessment (`docs/reviews/plugin-api-v2-14.12-verifier-assessment.md` on `lane/plugin-api-v2-rev14-draft`): the parser and local schema checks are stable; the checks that span several replies (authority, confirmation) keep producing findings and should be generated from the catalogue.
- **Example:** round 7 found that a title declared as `["string"]` instead of `"string"` was rejected: a checker bug holding up a contract seal.
- **Choices:** (a) as now: one seal, slow; (b) seal the text, catalogue and schemas on review, and treat the verifier as tested code with its own fixes and a fixture suite that the host and SDK must also pass.
- **Recommendation:** (b).

### 6. What must be pinned before Notes and the orchestrator cut over?

- **What:** the cutover gate requires eight things the contract does not yet carry (among them: browsing a note's history, comments from linked people, attachment upload, mention lookup, queued follow-ups, snooze presets, author and machine attribution on old transcript records, creating a collection). They are now listed as open and blocking.
- **Why now:** each one keeps its workflow disabled after cutover until a later revision pins it.
- **Detail:** the host lane wrote an example, the cost of waiting and a recommendation for each in `docs/morning-decisions.md` on `lane/plugin-api-v2-rev14-draft`.

### 7. Space microVM: how long does a sleeping space keep its snapshot, and what does erasing an account remove?

- **What:** a sleeping space's small VM is kept as a snapshot so it wakes in under half a second. The lane chose 24 hours provisionally; after that the next wake is a cold boot (not yet measured).
- **Example:** a space nobody opens over a weekend cold-boots on Monday. A space used daily never expires its scratch disk, because every sleep resets the clock. Erasing account A removes only snapshots A itself woke, not those of a shared space A used.
- **Choices:** retention 24 hours, 7 days, or by disk pressure; account erasure erases every snapshot of every space the account used (simple, costs other members a cold boot) or only its own.
- **Recommendation:** 7 days with a disk-pressure sweep; erase every snapshot of the spaces the account used. Written up on [issue #88](https://git.kayg.org/kayg/calternal-ai/issues/88).

### 8. Snapshot format

- **What:** two measured ways to keep a sleeping space: 256 MiB on disk with a 269 ms wake (p95), or 69 MiB with about 470 ms.
- **Choices:** smaller and slower, or larger and faster; the wake gate is 500 ms.
- **Recommendation:** the 69 MiB form: both pass the gate and disk is what limits how many sleeping spaces a host holds.

### 9. Always-on agents: default VM size and builds

- **What:** measured overnight: an idle always-on agent holds about 234 MiB of host memory in a 2 GiB guest (324 MiB in 4 GiB); three agents in one VM cost little more than one. Memory is not the limit; simultaneous builds are (CPU).
- **Example:** a 64 GiB host holds 48 to 54 two-GiB agent VMs by memory; eight builds at once already pushed wake latency to 744 ms.
- **Recommendation:** 2 GiB default, one build queue per host with CPU reserved for plugin wakes; unrestricted guests priced as fully backed memory.

- **Cost:** people who Tab through rows today must use arrows.
- **Recommendation:** yes.

### 12. iPad: which part of the sidebar is the middle column?
