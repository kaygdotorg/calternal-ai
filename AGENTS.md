# Calternal-AI working rules

- All UI implementation, visual design and UI/UX work MUST be done by Claude agents, never Codex/GPT agents. Non-Claude agents may implement backend/protocol/CLI logic and report UI findings, but route UI changes to Claude.
- User-approved overnight task, 2026-11-16: build the bounded roadmap in docs/tonight-contract.md after independent contract review. Use disposable development data only; no production migration, email, or unapproved external messaging.
- Maximum concurrent subagents (user rule, 2026-11-17): up to five Codex GPT-6.1-Sol medium lanes for backend work and two Claude lanes for UI. Spread builds across the dev VMs. Do not spawn descendants. Reuse or archive finished lanes.
- Defer product questions to docs/morning-decisions.md. Preserve existing protections and accepted decisions; missing safety proofs mean affected features remain disabled.
- Plugins are authored in TypeScript; portable GenUI first. Rust host and shared client core; Swift native UI through UniFFI; TypeScript browser. No Wasm.
- Full product architecture is in docs/architecture-proposal.md. The overnight build is a development preview, not proof of multi-tenant sandboxing, inherited full recovery/tiering, provider credential isolation, or production readiness.
- Machines (user rule, 2026-11-17; all reached over NetBird SSH). `hd01` (and `hd02`) are for editing, planning and administration only: do not build or run tests there. Build and test on the dev VMs (`calternal-dev-01-compute02`, `calternal-dev-02-std`). Measure performance only on the perf VMs (`calternal-perf-01-backup01`, `calternal-perf-02-backup01`), which are kept quiet: no builds there, and take the perf lock first. `calternal-macos-01-std` is for macOS performance and Apple-specific work; `kayg@std` (the Mac Studio) only for iPhone Simulator work and studying macOS apps through cua-driver. `calternal-cloud` is production: never touch it without explicit instruction. The bare-metal nodes (`std` beyond that one login, `compute01`, `compute02`, `backup01`) and every infraternal VM are off limits. Do not claim benchmark passes from development-host timings. Logins: `claude@calternal-dev-01-compute02` (x86_64, 12 cores; checkout at `~/Developer/Calternal-AI`), `ubuntu@calternal-dev-02-std` (aarch64), `lume@calternal-macos-01-std`, `kayg@calternal-perf-0{1,2}-backup01`; use these, not root. Build with `nix develop -c <command>` (see `flake.nix`). The dev VMs are shared with the existing app's work in the same accounts: do not touch its directories or processes.
- Do not overwrite another lane's files. Keep operation/GenUI contracts synchronized and commit only verified coherent work.
- Foundation work ports the existing app first (user rule, 2026-11-17). The reference is `/home/kayg/Developer/calternal` at `origin/dev`: its ADRs under `docs/adr/` are accepted decisions (storage layout ADR 0062 with the tiering amendment and `docs/plans/tiering-v3.md`, invites ADR 0059, roles as capability sets ADR 0058, groups ADR 0060), and its crates (`auth`, `store`, `fsio`, `notes`, …) are the starting code. Reuse and adapt them to spaces and the plugin architecture; do not redesign what they settle, and do not ask the user a question they answer. Read that repository with git only; never modify it.
- SQLite access is `rusqlite` only; never add `sqlx`.
- Every public item carries a doc comment complete enough to generate reference documentation; a code change updates its comment in the same edit. `scripts/check-docs.sh` is the gate.
- Backend lanes run on Codex: GPT-6.1-Sol medium for anything needing judgement (design, security boundaries, concurrency, reviews), GPT-6-Luna max for simple mechanical work (renames, moves, formatting, doc sweeps). UI stays with Claude (Sonnet 5.5 or Haiku 5.5, low or medium). When Codex is rate-limited, backend lanes run as Claude Opus 5.5 or Sonnet 5.5 at low or medium reasoning (by complexity) until it resets. Bring design questions that neither repository settles to the user instead of deciding them.
- Git workflow (user rule, 2026-11-17): `dev` is the working branch. Every lane works in its own bb worktree on its own branch cut from `dev` (`bb thread spawn --new-environment worktree --base-branch dev`), never in the shared checkout. The parent integrates each lane as small atomic commits on `dev`, pushes, then deletes the lane's branch and worktree once merged or no longer useful. `main` receives only verified working builds, rarely. Push to both `origin` (Forgejo) and `github` (public). Issues live on Forgejo only (`fj -H https://git.kayg.org ... -r kayg/calternal-ai`): every lane owns one issue and keeps it current. Issues stay concise and readable: a one-line goal, a status checklist, open questions as one-line bullets, links instead of logs.
- Human-readable files first (user rule, 2026-11-17): anything stored as a file in userdata is Markdown (frontmatter plus body, or `key: value` lines) unless that genuinely does not fit; JSON only then, with the reason written down.
- CLI (user rule, 2026-11-17): every `calternal` command prints structured, human-readable output by default (aligned tables, labelled fields, plain-language errors with the next step) and accepts `--json` for a stable machine-readable form with the same information. Human output adapts to the terminal width (columns drop or wrap by priority, never garbled), uses plain friendly language, and ends with a short hint toward the next useful command or `--help` where that helps. American spelling in command names (`enroll`).
- Review gate (user rule, 2026-11-17): before any lane merges into `dev`, it is reviewed against this checklist (from `docs/reviews/simplification-review-2026-11-17.md`); a failed item blocks the merge or is recorded on the lane's issue with a reason.
  1. No new copy of a shared type (IDs, caller-safe error, capabilities, time/hash helpers); "until shared types exist" is a blocker.
  2. Dependencies point downward; no crate added for one helper: move the helper down.
  3. Nothing global on the request path: no installation-wide mutex, thread or connection for per-space work; a lock held across fsync or a cross-thread call is justified in its doc comment.
  4. No blocking call on an async thread (file I/O, hashing, process spawn, SQLite, a std mutex held across I/O).
  5. Parse once, load once; the lane states the read and flush counts of its hot path.
  6. Constant work (schemas, catalogs, validators) is built once and cached.
  7. Everything stored has a stated bound or retention; "forever" needs the owner's sign-off.
  8. No compatibility code: no migration chains, legacy readers, aliases, interim projections, or ignored tests kept for old behaviour.
  9. Spaces only, by UUID: no names standing in for IDs, no "Home", no app-specific names in generic code.
  10. One place per fact: an operation, capability or role is declared once and the rest derived.
  11. No unwired code: every public item has a non-test caller in the merge, or the issue names the lane that will call it.
  12. Reuse before writing: the lane names the existing primitive it considered for files, durability, locking or validation.
  13. The docs gate covers the crate; comments state purpose, failure and cost, and do not restate the name.
  14. Docs match the code in the same merge (README, crate README, `docs/`); dated lane reports live under `docs/reviews/`.
  15. `cargo fmt --check` is clean; a source file past about 600 lines is split by concern.
- Official plugins are named `calternal-<name>` (`calternal-orchestrator`, `calternal-notes`); kinds keep short names (`threads`, `notes`).
- Every lane's report ends with a short "Simplification opportunities" section: what it noticed could be removed, merged or made simpler, in its own area or nearby.
