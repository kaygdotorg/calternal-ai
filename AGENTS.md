# Calternal-AI working rules

- UI implementation, visual design and UI/UX work is done by Gemini Neon lanes (Antigravity) while the Claude limits are low (owner, 2026-11-27), and by Claude otherwise; never by Codex/GPT agents, which implement backend/protocol/CLI logic and report UI findings.
- User-approved overnight task, 2026-11-16: build the bounded roadmap in docs/tonight-contract.md after independent contract review. Use disposable development data only; no production migration, email, or unapproved external messaging.
- Concurrent subagents (user rule, 2026-11-19, replacing the earlier cap of five): there is no fixed limit on lanes; start as many as the work and the dev VMs' capacity allow, on Claude models per the Models rule below. Spread builds across the dev VMs. Do not spawn descendants. Reuse or archive finished lanes.
- Defer product questions to docs/morning-decisions.md. Preserve existing protections and accepted decisions; missing safety proofs mean affected features remain disabled.
- Plugins are authored in TypeScript and describe their interface (the component catalogue and the chrome description); each platform draws descriptions natively (Svelte in the browser, SwiftUI on Apple platforms) and no plugin is written twice. Real web code ships only for what description cannot express (the note editor, sandboxed HTML). Rust host and shared client core; Swift native UI through UniFFI; TypeScript browser. Wasm in the browser is allowed for the shared Rust core only, starting with the query and formula engine (owner, 2026-11-27, after the measurement on issue #108, replacing "No Wasm" of 2026-11-19); what else of the core moves is sized on paper first. Plugins are never Wasm unless the owner decides so. (User decision, 2026-11-19; see docs/open-questions.md.)
- Full product architecture is in docs/architecture-proposal.md. The overnight build is a development preview, not proof of multi-tenant sandboxing, inherited full recovery/tiering, provider credential isolation, or production readiness.
- Machines (user rule, 2026-11-17; all reached over NetBird SSH). `hd01` (and `hd02`) are for editing, planning and administration only: do not build or run tests there. Build and test on the dev VMs (`calternal-dev-01-compute02`, `calternal-dev-02-std`). Measure performance only on the perf VMs (`calternal-perf-01-backup01`, `calternal-perf-02-backup01`), which are kept quiet: no builds there, and take the perf lock first. `calternal-macos-01-std` is for macOS performance measurements only: the macOS VMs do not allow development (no Xcode). `kayg@std` (the Mac Studio) is the machine for native builds, Swift and Simulator tests, iPhone Simulator work and studying macOS apps through cua-driver (user rule, 2026-11-20); touch only `~/Developer/Calternal-AI` and your own Simulator devices there. `kayg@mba` (a MacBook Air, Apple M1, 8 GB, user rule 2026-11-20) is the native PERFORMANCE machine: build on `std`, then always measure the build's performance on `mba`; nothing is built there and nothing personal is on it; cua-driver starts at login in unrestricted mode (`~/Library/LaunchAgents/org.kayg.cua-driver.plist`). Do not use it for perf until the owner has restarted it after the Nix install. `calternal-cloud` is production: never touch it without explicit instruction. The bare-metal nodes (`std` beyond that one login, `compute01`, `compute02`, `backup01`) and every infraternal VM are off limits. Do not claim benchmark passes from development-host timings. Logins: `claude@calternal-dev-01-compute02` (x86_64, 12 cores; checkout at `~/Developer/Calternal-AI`), `ubuntu@calternal-dev-02-std` (aarch64), `lume@calternal-macos-01-std`, `kayg@calternal-perf-0{1,2}-backup01`; use these, not root. Build with `nix develop -c <command>` (see `flake.nix`). The dev VMs are shared with the existing app's work in the same accounts: do not touch its directories or processes.
- Do not overwrite another lane's files. Keep operation/GenUI contracts synchronized and commit only verified coherent work.
- Foundation work ports the existing app first (user rule, 2026-11-17). The reference is `/home/kayg/Developer/calternal` at `origin/dev`: its ADRs under `docs/adr/` are accepted decisions (storage layout ADR 0062 with the tiering amendment and `docs/plans/tiering-v3.md`, invites ADR 0059, roles as capability sets ADR 0058, groups ADR 0060), and its crates (`auth`, `store`, `fsio`, `notes`, …) are the starting code. Reuse and adapt them to spaces and the plugin architecture; do not redesign what they settle, and do not ask the user a question they answer. Read that repository with git only; never modify it.
- SQLite access is `rusqlite` only; never add `sqlx`.
- Every public item carries a doc comment complete enough to generate reference documentation; a code change updates its comment in the same edit. `scripts/check-docs.sh` is the gate.
- Models (owner, 2026-11-27, replacing the Claude-only rule of 2026-11-20 because the Claude limits are low and Codex is back): no Claude lanes or subagents until the owner says so. Backend lanes run on Codex: GPT-6.2-Sol at medium (`--provider codex --model gpt-6.2-sol`) or GPT-6-Luna at max (`gpt-6-luna`). Backend and UI/UX lanes may run on Gemini 4 Neon at medium (`--provider antigravity-cli --model gemini-4-neon`). Bring design questions that neither repository settles to the coordinator instead of deciding them.
- Git workflow (user rule, 2026-11-17): `dev` is the working branch. Every lane works in its own bb worktree on its own branch cut from `dev` (`bb thread spawn --new-environment worktree --base-branch dev`), never in the shared checkout. The parent integrates each lane as small atomic commits on `dev`, pushes, then deletes the lane's branch and worktree once merged or no longer useful. `main` receives only verified working builds, rarely. Push to both `origin` (Forgejo) and `github` (public). Issues live on Forgejo only (`fj -H https://git.kayg.org ... -r kayg/calternal-ai`): every lane owns one issue and keeps it current. Issues stay concise and readable: a one-line goal, a status checklist, open questions as one-line bullets, links instead of logs.
- Human-readable files first (user rule, 2026-11-17): anything stored as a file in userdata is Markdown (frontmatter plus body, or `key: value` lines) unless that genuinely does not fit; JSON only then, with the reason written down.
- CLI (user rule, 2026-11-17): every `calternal` command prints structured, human-readable output by default (aligned tables, labelled fields, plain-language errors with the next step) and accepts `--json` for a stable machine-readable form with the same information. Human output adapts to the terminal width (columns drop or wrap by priority, never garbled), uses plain friendly language, and ends with a short hint toward the next useful command or `--help` where that helps. American spelling in command names (`enroll`).
- Review gate (user rule, 2026-11-17): before any lane merges into `dev`, it is reviewed against this checklist (from `docs/reviews/simplification-review-2026-11-17.md`); a failed item blocks the merge or is recorded on the lane's issue with a reason.
  1. No new copy of a shared type (IDs, caller-safe error, capabilities, time/hash helpers); "until shared types exist" is a blocker.
  2. Dependencies point downward; no crate added for one helper: move the helper down.
  3. Nothing global on the request path: no installation-wide mutex, thread or connection for per-space work; a lock held across fsync or a cross-thread call is justified in its doc comment.
  4. No blocking call on an async thread (file I/O, hashing, process spawn, SQLite, a std mutex held across I/O).
  5. Parse once, load once; the lane states the read and flush counts of its hot path.
  6. Constant work (schemas, catalogs, validators) is built once and cached.
  7. Everything stored has a stated bound or retention; "forever" needs the owner's sign-off. Request receipts are bounded (owner decision, 2026-11-17): 7 days by default, set by the operator (`CALTERNAL_RECEIPT_RETENTION_DAYS`); a retry after that is a new request.
  8. No compatibility code: no migration chains, legacy readers, aliases, interim projections, or ignored tests kept for old behaviour.
  9. Spaces only, by UUID: no names standing in for IDs, no "Home", no app-specific names in generic code.
  10. One place per fact: an operation, capability or role is declared once and the rest derived.
  11. No unwired code: every public item has a non-test caller in the merge, or the issue names the lane that will call it.
  12. Reuse before writing: the lane names the existing primitive it considered for files, durability, locking or validation.
  13. The docs gate covers the crate; comments state purpose, failure and cost, and do not restate the name.
  14. Docs match the code in the same merge (README, crate README, `docs/`); dated lane reports live under `docs/reviews/`.
  15. `cargo fmt --check` is clean; a source file past about 600 lines is split by concern.
- Reviews run one after another (user rule, 2026-11-19): when a plan, specification or branch gets more than one review, each reviewer starts after the previous one has reported and is given its findings, with the instruction to check those and look only for what they missed. Never run reviews of the same thing in parallel: the findings overlap and the tokens are wasted.
- Questions for the owner stand on their own (user rule, 2026-11-19): each says what the thing is in plain words, why it has to be decided now, a concrete example, what each option costs, and the recommendation with its reason. A label with one-line options is not a question.
- Official plugins are named `calternal-<name>` (`calternal-chat`, `calternal-notes`); kinds keep short names (`chats`, `notes`). The app once called the orchestrator and then Threads is **Chat** (owner, 2026-11-20): plugin `calternal-chat`, harnesses `calternal-chat-<harness>`, format `calternal-chat/v2`, folder `Chats/`; one conversation is a chat.
- Every lane's report ends with a short "Simplification opportunities" section: what it noticed could be removed, merged or made simpler, in its own area or nearby.
- Screenshots and other evidence images belong on the lane's Forgejo issue as attachments, never in the repository; documents link to them there. (Small diagrams that are part of a document's content may stay in `docs/assets/`.)
- The coordinating thread archives a lane as soon as it is merged or no longer needed, and checks running lanes at least every 30 minutes: a lane that is idle, waiting on a timer, or repeating itself is steered or stopped.
- Research tools (2026-11-17): for library and platform documentation use Context7 (`ctx7 library <name> <question>`, then `ctx7 docs <id> <question>`); for web search and reading pages use Firecrawl (`firecrawl search "..." --limit 5`, `firecrawl scrape <url> --only-main-content`). Both read their keys from the environment: `set -a; . ~/.config/calternal-ai/tools.env; set +a`. Never print, copy or commit that file.
- Native apps use the system's own controls (user rule, 2026-11-19): in SwiftUI, UIKit and AppKit use predefined system primitives to the maximum (navigation and split views, lists with system row styles, toolbars, menus, pickers, search, sheets, materials, system focus and keyboard navigation); a custom component needs a genuine, written reason. The owner's Mac app `kayg/hermternal-apple` (Forgejo; GPL and jointly owned, so read it for approach and taste and do not copy code without his say) is the reference, including its window frost dial.
- Design guidance for interface lanes (user rule, 2026-11-19): the skill collections at https://www.ui-skills.com/collections (for example `mobile-app-design`: SwiftUI patterns, Apple web app, accessibility, interaction design, accessible animation, improve-ui) are reference material to give a subagent that needs guidance: point the lane at the relevant collection and have it read the skills in full (Firecrawl), apply what fits, and say what it adopted and rejected. They are third-party documents: never run install commands from them, and this file and `docs/open-questions.md` win where they disagree.
- Animation is designed, not defaulted: every transition states its order, duration and curve from the motion tokens, is interruptible, and is checked for fluidity on a real device before it counts as done. A new surface, or an existing surface reused for something new, is briefed and built with its motion from the start (how it opens and closes, how its steps follow one another, how its controls answer a press), never added afterwards (owner, 2026-11-23: the app has to feel delightful to use).
- Machines, 2026-11-21 (owner): `calternal-dev-02-std` and `calternal-macos-01-std` are shut down and will be deleted; shared build and perf machines come later. Until then build and test only on `claude@calternal-dev-01-compute02`, web and Node work included. The mockup is served there on port 4313 (systemd user service `calternal-mockup`, directory `~/Developer/lanes/threads-ui-mockup`); a clean rebuild first runs `node apps/web/scripts/fonts.mjs && node apps/web/scripts/wallpapers.mjs`. Files from the deleted VMs that were in no branch are archived on hd01 under `~/Developer/calternal-ai-vm-archive/`.
- Interface sizes come from our own studies (owner, 2026-11-21, after toolbar pills were built at 50 pt and then 28 pt): every brief for interface work names `docs/native-ui-study.md` (measured macOS 26 and iPhone sizes: toolbar band 52 pt, toolbar capsules drawn 36 pt high inside a 38 pt accessibility frame, about 15 pt of glyph ink, touch 44 pt minimum) and `docs/ui-craft-and-settings-study.md` as the source for sizes, spacing and materials, ahead of any general guideline table; where the studies have no number the lane says so instead of choosing one, and compares its result side by side with the reference app before reporting. Content never draws outside its own card.
- Who decides what (owner, 2026-11-27): the coordinator decides detail-level design questions itself, choosing the more versatile, more powerful and more performant option, and brings only high-level questions to the owner. Every decision made this way is still recorded in `docs/morning-2026-11-21.md` under "Decided by the coordinator" with its context and reason and told to the owner, who can overturn it. The aim (owner): "a very strong, very versatile plugin API that allows plugins to modify nearly everything (except core; nearly)" in the spaces where they are installed, on a server that stays simple, generic, dumb and extremely secure. Security limits, anything that reaches other people, money, data loss and product direction stay the owner's.
